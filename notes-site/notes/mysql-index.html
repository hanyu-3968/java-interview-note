区分度选列，最左前缀匹配，覆盖索引免回表，EXPLAIN 验证。

一、索引底层：B+ 树为什么快

叶子存数据 + 双向链表，3 层管 2000 万行。

InnoDB 的索引是 B+ 树：所有数据存在叶子节点，非叶子节点只存索引键 + 子节点指针，叶子节点之间用双向链表连接。

特征说明记忆画面
多路平衡树高通常 3~4 层大楼楼层索引，3 层定位到房间
叶子存数据真正行数据只在叶子仓库货架在最底层，楼上只放目录牌
叶子链表叶子节点双向链表字典页码连成一条线，范围翻页快
3 层存 2000 万行单节点 16KB，约 1000 个键，1000³ ≈ 10 亿三级目录管千万行，三次 IO 搞定

补充：聚簇索引（主键索引，叶子存整行数据）和二级索引（非主键索引，叶子存主键值）用途不同。二级索引查到主键后还要去聚簇索引取整行，这就是"回表"。

二、选择性原则：区分度决定要不要建

区分度越高越值得建，低于 0.3 要三思。

区分度 = count(distinct col) / count(*)，越接近 1 越适合建索引。

区分度典型列是否建索引记忆画面
接近 1身份证号、订单号、UUID✅ 强烈推荐一人一个号，一查就中
0.5~0.9用户名、手机号✅ 推荐大多数不重复
0.1~0.3性别、状态、是否删除❌ 不推荐全表一半都是男，筛不掉多少
接近 0布尔标志、固定枚举❌ 不建翻完索引还得翻大半张表

补充：区分度低不是"绝对不能建"，若作为联合索引的最后一列配合高区分度列做覆盖，仍可能有用。判断标准是"过滤后还剩多少行"，不是单看列本身。

三、最左前缀原则：联合索引的匹配规则

从左到右连续匹配，遇到范围查询就断。

联合索引 (a, b, c) 按 a → b → c 顺序排好，查询必须从最左列开始，不能跳过中间列。

查询条件是否走索引原因记忆画面
where a=1✅ 用到 a从最左列开始查字典先翻首字母
where a=1 and b=2✅ 用到 a,b连续匹配首字母 + 第二字母
where a=1 and b=2 and c=3✅ 全用完整匹配三级目录全命中
where b=2❌ 不走跳过 a直接翻第二字母，目录失效
where a=1 and c=3⚠️ 只用 a跳过 b，c 失效中间隔一层，c 用不上
where a=1 and b>2 and c=3⚠️ 用 a,bb 是范围，c 失效范围之后目录断了

补充："最左前缀"指索引列的顺序，不是 WHERE 的书写顺序。where b=2 and a=1 优化器会自动调整为 a、b 顺序，仍能走索引。但跳过中间列（如 a、c 跳过 b）则无法补齐。

四、覆盖索引：免回表就是快

查询列全在索引里，直接从索引树返回。

场景索引是否回表性能
select * from t where a=1(a)✅ 回表慢：索引查到主键 → 再查聚簇索引
select a,b from t where a=1(a,b)❌ 不回表快：索引里就有 a、b
select a,b,c from t where a=1(a,b,c)❌ 不回表快：覆盖索引
select a,b,c,d from t where a=1(a,b,c)✅ 回表慢：d 不在索引里

补充：覆盖索引不是一种"索引类型"，而是"查询恰好被索引覆盖"的使用状态。EXPLAIN 里看到 Extra: Using index 就说明走了覆盖索引，不需要回表。

五、控制索引数量：不是越多越好

单表 5~6 个以内，每个都要有高频查询对应。

影响维度说明记忆画面
写入变慢insert/update/delete 要同步更新所有索引每加一本书要更新 N 个目录
占用空间每个索引一棵 B+ 树目录本身也占书架
优化器选择困难多个可用索引时选错路太多反而迷路
单表建议5~6 个以内一本书 5~6 个目录够用了

补充："单表 5~6 个"是经验值不是硬上限。核心判断是每个索引都要有高频查询对应，没人查的索引就是纯负担。建索引前先看慢查询日志，确认这列真的被频繁过滤。

六、索引失效场景：七大杀手

索引列被加工（函数/转换/模糊/运算）就失效。

失效场景错误写法正确写法记忆画面
左模糊like '%abc'like 'abc%'字典从后往前翻，目录废了
函数操作where year(t)=2024where t between '2024-01-01' and '2024-12-31'先加工再查，索引认不出
隐式类型转换where phone=13800138000（phone 是 varchar）where phone='13800138000'数字对字符串，被转成函数
违反最左前缀联合索引 (a,b,c) 查 where b=2where a=1 and b=2跳过最左列，目录失效
范围后列失效where a=1 and b>2 and c=3把范围列放最后范围之后断链
!= / NOT INwhere status != 1改用 in (2,3,4) 或拆分否定条件优化器难走索引
OR 两侧未都有索引where a=1 or b=2（b 无索引）给 b 也建索引，或拆成 union一边没索引就退化全表扫

补充：!= 不是绝对失效，区分度高时仍可能走索引，但优化器通常判断"过滤后行数仍多"而放弃。OR 也不是绝对失效，只有当 OR 两侧至少有一列无索引时才退化全表扫；两侧都有索引时走 index_merge。like 'abc%'（右模糊）能走索引，只有左模糊 %abc 和全模糊 %abc% 才失效。

七、EXPLAIN 验证：用执行计划说话

看 type 不是 ALL、key 不是 NULL、Extra 有 Using index。

列关注点好信号坏信号
type访问类型const / eq_ref / ref / rangeALL（全表扫）
key实际用的索引命中预期索引NULL（没用索引）
rows预估扫描行数越小越好接近全表行数
Extra附加信息Using index（覆盖索引）Using filesort / Using temporary

type 从好到差排序：const > eq_ref > ref > range > index > ALL

补充：type=index 看起来像走索引，其实是扫描整棵索引树（比 ALL 稍好但仍是全扫），通常出现在 select count(*) 或查询列全在索引里但无 where 过滤时。真正"用索引定位"是 ref/range 及以上。

八、高频场景题

查询变慢先 EXPLAIN，对照七大失效场景排查。

查询突然变慢，怎么判断是不是索引失效？

先 EXPLAIN 看 type 是否退化成 ALL、key 是否变 NULL，再对照 SQL 检查七大失效场景（左模糊、函数、隐式转换、跳最左、范围后断、否定条件、OR 单边）。

联合索引 (a,b,c)，where a=1 and c=3 走索引吗？

只走 a，c 用不上。因为跳过了 b，B+ 树在 a 之后无法直接定位 c。要么改成 a=1 and b=? and c=3，要么把 c 单独建索引，或调整联合索引顺序为 (a,c,b)。

性别字段要不要建索引？

单独建没意义——区分度太低，过滤后仍剩一半行，优化器宁可全表扫。但如果是联合索引 (status, user_id) 配合高区分度列做覆盖，仍可能有用。判断标准是"过滤后还剩多少行"。

为什么 select * 慢，select 指定列快？

select * 必然回表（聚簇索引取整行），而 select 指定列若被索引覆盖则 Using index 免回表。所以高频查询要建覆盖索引，把查询列都包进联合索引。

九、面试回答模板

本质是查询加速与写入成本的平衡，用 EXPLAIN 验证。

问题本质是索引设计要在"查询加速"和"写入维护成本"之间找平衡，不是越多越好，也不是有索引就一定快。

机制是 InnoDB 用 B+ 树存索引，3 层可管 2000 万行；联合索引按最左前缀匹配，覆盖索引可免回表；但函数、隐式转换、左模糊等会让索引失效退化为全表扫。

实战中我会先按区分度选列、按查询顺序排联合索引、用覆盖索引减少回表、控制单表索引 5~6 个以内，最后用 EXPLAIN 验证 type 不是 ALL、Extra 有 Using index，确保索引真的被用上。
