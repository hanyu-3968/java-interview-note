Docker 打包 + K8s 编排 + Serverless 托管 + 混合云选型。

一、什么是云原生

方法论不是工具，四件套闭环才是云原生。

云原生（Cloud Native）是一套构建和运行应用程序的方法论，核心思想是充分利用云平台的弹性、分布式、自动化能力，让应用本身具备弹性、可观测性、韧性和自动化能力。

  • 不是"把地搬到云上"（lift and shift），而是为了云而设计。
  • 完整闭环：容器打包 + 微服务拆分 + K8s 编排 + 声明式 API 描述期望状态。
  • 终极目标：业务开发只管写代码，弹性、容错、运维全交给平台。
维度传统应用云原生应用
部署单元虚拟机 + 脚本容器镜像
扩缩容手动加机器声明式自动扩缩
故障处理人工介入自愈、自动恢复
运维边界开发运维不分家平台兜底运维

补充：云原生 ≠ 用了 Docker 和 K8s。用了容器但架构仍是单体、扩缩容靠手动，只是"容器化部署"而非云原生。云原生强调声明式 API + 弹性自愈 + 可观测的闭环。

二、Docker：容器化打包平台

应用+依赖打包成镜像，秒级启动、相互隔离。

Docker 是容器化平台，把应用和依赖一起打包成镜像，镜像可在任何支持 Docker 的环境快速运行，容器之间相互隔离，启动快、占用资源少。

能力说明
快速部署交付镜像即"可执行的环境"，秒级启动
资源隔离每个容器互不影响
弹性伸缩配合 K8s 大规模自动扩缩
环境一致开发/测试/生产同镜像

补充：容器 vs 虚拟机——虚拟机带完整客户机 OS，启动分钟级、GB 级内存开销；容器共享宿主内核，启动秒级、MB 级开销，但隔离性弱于虚拟机。

项目中如何用 Docker

场景用法
本地开发docker-compose 一键起数据库、缓存、消息队列
打包镜像写 Dockerfile，应用+依赖一起打包
自动化部署CI/CD 流水线自动构建镜像并部署
多环境切换不同配置文件 + 环境变量切开发/测试/生产
服务编排生产用 K8s 管多容器，高可用+弹性伸缩

三、Kubernetes：容器编排平台

声明式 API 是灵魂，Pod 最小调度，自愈+弹性。

Kubernetes（K8s）是开源的容器编排平台，用于自动化容器化应用的部署、扩缩容、管理和运维，帮助高效管理大规模容器集群，实现服务高可用、弹性伸缩、自动恢复。

核心能力说明
声明式 API描述"期望状态"，系统自动趋近
自动调度把 Pod 调度到合适节点
弹性扩缩HPA 按 CPU/自定义指标扩副本
自愈容器挂了自动重启、节点挂了自动迁移
服务发现Service 提供稳定访问入口

补充：Docker vs K8s——Docker 解决"怎么打包和跑一个容器"（单机视角），K8s 解决"怎么管成百上千个容器"（集群视角），K8s 底层仍跑 Docker/containerd 容器。声明式 vs 命令式：命令式一步步教，声明式描述期望状态由系统调谐，云原生核心是声明式。

四、Serverless：执行模型的极致托管

写代码、传函数、平台跑、按调用付费。

Serverless 是一种云计算架构模式，核心理念是你只负责写代码，不用管服务器在哪、怎么跑、怎么扩容。它是云原生的一种执行模型：开发者编写函数代码上传，云平台自动管理服务器、运行时、伸缩，按函数调用次数和资源消耗计费。

维度传统开发Serverless
服务器先买服务器、装系统、配环境代码交给云平台
扩容手动加机器平台自动分配资源
计费按服务器时长按调用次数+资源消耗
感知看得见服务器感觉不到服务器存在

补充：Serverless ≠ 没有服务器，服务器仍存在只是由云平台托管、开发者无感知。Serverless 适合事件驱动、短时、突发场景（webhook、定时任务、图片处理）；不适合长连接、稳态高流量、超低延迟场景（冷启动有延迟），这类用容器+K8s 更合适。

五、云原生如何优化启动速度

瘦镜像、懒加载、异步启动、提前备。

云原生应用通常跑在容器环境（如 K8s），具备弹性伸缩、自动恢复、按需调度等能力，应用启动速度直接影响这些能力的发挥。容器相比虚拟机启动快（共享内核），但镜像过大依然会拖慢速度，因此轻量级容器镜像是云原生优化的核心方向之一。

优化招做法原理
镜像瘦身多阶段构建、Alpine/distroless 基础镜像、.dockerignore 排除无关文件镜像越小拉取越快、启动越快
延迟加载先让程序跑起来，非核心模块懒加载核心路径先就绪，边跑边加载
异步化启动启动时不做耗时操作，数据库初始化、海量配置加载改异步或预热启动线程不被阻塞
提前准备配置、缓存、依赖提前就绪，启动时直接用减少启动期 IO 和等待

补充：启动快 ≠ 运行快——启动优化解决的是弹性伸缩响应速度和故障恢复时间，不是吞吐量优化。镜像瘦身不是越小越好，瘦到丢失运行时依赖（JRE、glibc）会跑不起来，多阶段构建是主流平衡手段。

六、混合云选型：为什么不全上公有云

核心数据私有留，弹性高峰公有扛，专线打通。

混合云是公有云 + 私有云的组合，通过专线或 VPN 打通，兼顾合规、成本和弹性。

维度放在哪原因
核心数据私有云用户身份、财务记录等合规要求必须留本地
业务高峰公有云电商大促需要快速弹性扩容
静态页面公有云非敏感内容放公有云降低成本
非敏感计算公有云成本低、弹性好
网络打通专线/VPN公有云与私有云互通

补充：混合云 vs 多云——混合云是"公有+私有"两种部署形态组合，解决合规与弹性矛盾；多云是"同时用多家公有云"，解决厂商锁定与择优。混合云不是临时把数据搬到公有云，核心数据始终在私有云，数据流向受合规约束。

七、高频场景题

启动慢、混合云选型、Serverless 适用场景。

"云原生应用启动慢，弹性伸缩跟不上，怎么优化？"

先看启动瓶颈在哪一层：镜像拉取慢、启动期阻塞、还是依赖初始化慢。镜像层用多阶段构建 + Alpine 瘦身，拉取慢可配镜像预热和 P2P 分发；启动期阻塞把数据库连接、海量配置加载改异步或预热，先让健康检查端口就绪；依赖初始化用懒加载，核心路径先跑起来。目标是把启动从分钟级压到秒级，HPA 才能真正跟得上流量突增。

"为什么选混合云而不是全公有云？"

核心矛盾是合规与弹性的取舍。用户身份、财务记录这类数据合规要求必须留在私有云，不能上公有云；但电商大促这种业务高峰需要公有云的快速弹性扩容，私有云扩容慢且闲置成本高。所以核心数据留私有云、弹性高峰和非敏感计算放公有云、静态页面也放公有云降成本，通过专线或 VPN 打通形成混合云。全公有云在合规上过不了关，全私有云在弹性上扛不住高峰。

"Serverless 适合什么场景，什么场景不适合？"

适合事件驱动、短时执行、突发流量的场景：webhook 回调、定时任务、图片/视频处理、IoT 消息处理。这些场景调用频次不均匀，按调用计费比常驻服务器便宜，且无需运维。不适合长连接、稳态高流量、超低延迟的场景：长连接会被函数超时切断，稳态流量按调用计费反而比容器贵，冷启动延迟对低延迟服务是硬伤。这类场景用容器 + K8s 更合适。

八、面试回答模板

本质→机制→实战，三句话讲清一题。

问题本质是……（先说云原生问的是哪一层：方法论、容器化、编排、执行模型、还是选型）。

机制是……（解释原理 + 关键组件），因为……（为什么这样设计）。

实战中我会……（落地手段 + 取舍），例如……（具体场景）。

例：问"什么是云原生"——本质是一套构建和运行应用的方法论，不是把地搬到云上而是为云而设计；机制是容器打包 + 微服务拆分 + K8s 编排 + 声明式 API 描述期望状态，让系统具备弹性、可观测、自愈能力；实战中我会用 Docker 打镜像、K8s 做编排和 HPA 弹性、配合可观测性组件，业务只管写代码，运维交给平台。

九、最后复习：闭眼回忆 8 句

方法论→Docker→K8s→Serverless→启动优化→混合云。

  1. 云原生：方法论不是工具，容器+微服务+K8s+声明式 API 四件套，目标是弹性、可观测、自动化闭环。
  2. Docker：应用+依赖打包成镜像，容器共享内核秒级启动，Compose 起依赖、Dockerfile 打镜像、CI/CD 自动部署。
  3. 容器 vs 虚拟机：容器共享内核轻量但隔离弱，虚拟机带完整 OS 重但隔离强。
  4. K8s：容器编排平台，声明式 API 是灵魂，Pod 是最小调度单元，Service 稳定入口，HPA 弹性扩缩，自愈自动恢复。
  5. Serverless：执行模型不是没有服务器，写函数、平台跑、按调用计费，适合事件驱动短时突发，不适合长连接稳态低延迟。
  6. 启动优化：镜像瘦身（多阶段+Alpine）、延迟加载、异步启动、提前准备——四招把启动压到秒级。
  7. 混合云：核心数据私有留合规、弹性高峰公有扛、静态内容公有放降本、专线 VPN 打通；区别于多云（多家公有云）。
  8. 易混：云原生 ≠ 用了 Docker/K8s；Serverless ≠ 没服务器；启动快 ≠ 运行快；混合云 ≠ 多云。

十、怎么练才记得住

主动回忆四法，别反复通读。

  1. 每次只看一个小节，遮住表格，先自己说出"概念 → 机制 → 易混点 → 落地场景"，再对照。
  2. 用"高频场景题"的 3 道题各讲 30 秒；卡住时只回看对应小节。
  3. 隔天再讲一遍，换成自己的项目例子；能解释"为什么选混合云、为什么用 Serverless、启动慢怎么查"才算会。
  4. 复习时轮流画"云原生总图"和"混合云选型表"；能默写出四件套和启动优化四招才算熟。
