CPU 飙高 5 步定位 + GC 现象猜根因 + 参数调优闭环。

一、CPU 飙升的 5 大元凶

码线多外配：代码、并发、流量、IO、配置。

类别典型场景一句话根因
① 代码逻辑 while(true) 死循环、正则灾难性回溯、频繁创建临时对象引发 GC 线程在疯狂运算或频繁 GC，CPU 全被吃掉
② 线程并发 CAS 自旋锁反复失败、线程池过大导致频繁上下文切换 线程在空转等待或频繁切换，CPU 空耗
③ 外部 IO 日志打印过多、频繁磁盘 IO/网络 IO 频繁用户态↔内核态切换，系统调用开销大
④ JVM 配置 堆内存太小频繁 GC、栈内存太小、JIT 编译过热 GC 线程占用大量 CPU，或 JIT 编译过热
⑤ 流量激增 秒杀/大促流量暴涨、监控工具/日志轮转脚本抢占 CPU 请求量过大，工作线程飙升，超出系统承载

记忆口诀：码线多外配——码（代码逻辑）、线（线程并发）、多（流量激增）、外（外部 IO）、配（JVM 配置）。

补充：CPU 飙高不一定是业务代码问题。GC 线程忙（堆太小）、锁竞争空转（线程池过大）、系统进程抢占（监控脚本）都会让 CPU 飙高。先 top 看是 java 进程自身占高还是系统进程，再决定排查方向。

二、CPU 飙升 · 5 步定位法

进→线→转→栈→判，从进程到代码行。

步骤命令做什么
1top / htop找出高 CPU 进程 PID
2top -H -p <PID>找出该进程内高 CPU 线程 TID
3printf "%x\n" <TID>线程 ID 转十六进制
4jstack <PID> | grep -A 30 <十六进制TID>定位该线程正在执行的代码行
5按堆栈类型判断GC 线程→jstat；业务线程→查死循环；锁竞争→Arthas

记忆口诀：进→线→转→栈→判（进程→线程→转 16 进制→堆栈→判断）。

三、JVM 优化核心命令

-Xms=-Xmx 避免扩容，DisableExplicitGC 禁人为 GC。

命令/参数作用示例
java -X查看非标准参数列表java -X
-Xms / -Xmx堆内存初始值 / 最大值java -Xms512m -Xmx2048m TestJVM
-XX:+DisableExplicitGC禁用 System.gc() 调用-XX:+DisableExplicitGC
jstat -gcutil实时查看 GC 状态jstat -gcutil 25048 5000 100
jmap -dump导出堆内存快照（会 STW）jmap -dump:live,format=b,file=heap.hprof 25048

堆内存调优原则：

  • -Xms = -Xmx：设为相同，避免运行时动态扩容/缩容的性能损耗。
  • -Xmx：取物理内存的 60%~70%，留出空间给元空间、栈内存、操作系统。
  • 新生代占比：堆的 1/3 ~ 1/4，避免新生代太大导致 YGC 时间过长。

补充：-Xms 和 -Xmx 设为相同不是"浪费内存"，而是避免堆动态扩容时的内存申请、缺页中断、GC 暂停增加。生产环境宁可"浪费"一点内存，也不要不可预测的性能抖动。

四、问题类型快速判断

泄不降，快降半，元不动，频不高。

观察现象根因应对策略
老年代持续增长，FGC 后几乎不降 内存泄漏（强引用链未断开） 导出 Heap Dump → MAT 找 GC Roots
老年代增长快，FGC 后回收大部分 临时对象晋升过快 / Survivor 区太小 调大新生代或 Survivor 区比例
元空间持续增长，FGC 无法回收 类加载器泄漏（动态生成类未卸载） 检查 CGLib 代理/热部署场景
FGC 频繁，但老年代占用不高 代码中调用了 System.gc() 加 -XX:+DisableExplicitGC 禁用

记忆口诀：泄不降，快降半，元不动，频不高——对应四种 GC 现象。

五、JVM 内存模型

线程私有（计数器、栈）+ 线程共享（堆、方法区）。

线程私有（随线程生灭）：

  • 程序计数器：记录当前线程执行到哪一行字节码。
  • 虚拟机栈：执行 Java 方法，每个方法对应一个栈帧（含局部变量表、操作数栈等）。

线程共享（所有线程共用）：

  • Java 堆：存放几乎所有对象实例和数组，GC 主要发生地，分新生代和老年代。
  • 方法区：存储类信息、常量、静态变量、Class 对象；JDK8 后改为元空间（Metaspace），使用本地内存。
版本堆内存结构方法区位置
JDK 7 及以前新生代 + 老年代 + 永久代永久代（堆内，-XX:MaxPermSize 限定）
JDK 8 及以后新生代 + 老年代元空间（移出堆，使用本地内存）

补充：方法区是 JVM 规范定义的逻辑区域，永久代和元空间都是它的实现。JDK8 把实现从"堆内的永久代"换成"本地内存的元空间"，不是"取消方法区"。移出堆的原因是永久代大小固定容易 OOM，元空间用本地内存默认几乎无限，动态加载类更灵活。

六、面试串联话术

现象→工具→根因→修复一气呵成。

线上 CPU 飙高，我会按这个思路快速排查：第一步用 top -H -p 找到最忙的线程 ID，转成十六进制后用 jstack 定位到具体代码行。

第二步看堆栈指向哪里——如果是 GC 线程在忙，就用 jstat 看 GC 频率，再结合 jmap 导出堆 Dump 用 MAT 分析；如果是业务线程，就检查是否有死循环或正则回溯。

第三步根据分析结果调整 JVM 参数。比如堆内存太小导致频繁 GC，就把 -Xmx 调大，同时让 -Xms 等于 -Xmx 避免动态扩容；如果发现 System.gc() 被频繁调用，就加上 -XX:+DisableExplicitGC 禁用。

最后，如果是流量激增导致的工作线程飙升，光调 JVM 没用，需要限流或扩容。JVM 参数调优是兜底，真正的根治还是要优化代码和架构。
