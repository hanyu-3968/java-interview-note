一、ApplicationListener · 事件驱动解耦

单体应用内解耦最优解，轻量无依赖。

轻量级解耦的"最优解"。事件驱动模式遵循开闭原则（对扩展开放，对修改关闭），在业务复杂的项目中，能有效降低核心模块的修改频率和风险。

对比维度ApplicationListener（Spring 事件）接口调用（同步/异步）消息队列（MQ）
核心优势极轻量，无额外依赖，代码耦合度低实现简单直接，适合强依赖的同步场景可靠性极高，支持重试、削峰填谷，系统间彻底解耦
适用场景单体应用内部的模块解耦，如启动初始化、简单的业务联动同步 RPC 调用，需要实时获取返回值分布式系统间的异步通信，如跨服务的订单、支付通知
性能与资源性能最高，基于 JVM 内存依赖网络 IO，同步调用会阻塞线程性能较高，但需独立部署 Broker，有额外运维成本
可靠性一般，异常会影响主流程；若需重试，需自行实现同步调用可靠性高；异步回调失败需自行处理最高，有持久化和重试机制，失败消息可回溯
系统依赖无，仅依赖 Spring 框架无，仅依赖服务提供方需额外搭建和维护 MQ 集群

补充：ApplicationListener 是单体应用内的解耦方案，不是分布式解耦。跨服务异步通信还是要用 MQ，ApplicationListener 只解决同一 JVM 内模块间的耦合。

二、Bean 扩展点三剑客

BFPP 改图纸，BPP 改成品，Aware 拿容器。

特性BeanFactoryPostProcessorBeanPostProcessorApplicationContextAware
执行时机Bean 定义加载后，实例化前Bean 实例化后，初始化前后Bean 实例化 + 属性注入后，初始化前
操作对象BeanDefinition（元数据）Bean 实例（对象）当前 Bean 自身
执行次数全局一次每个 Bean 都会触发每个实现类触发一次
典型用途修改 Bean 定义、占位符解析AOP 代理、属性校验、包装增强获取容器资源（ApplicationContext 等）
是否常见较少直接写（框架内部用得多）较常见（尤其是 AOP 场景）较常见（尤其写工具类）

什么时候必须用 BeanPostProcessor：

  • @Aspect 只能拦截方法调用，无法替换掉整个 Bean。但 BeanPostProcessor 可以：返回一个完全不同的对象（比如 Mock 对象用于测试）、为 Bean 动态添加新的接口实现。
  • 如果只是想给某个方法加日志、监控、权限校验，用 @Aspect 就够了，简单直接。
  • 如果需要修改 Bean 本身、替换掉它、或者在它初始化之前动手脚，那就必须用到 BeanPostProcessor。

补充：BeanFactoryPostProcessor 操作的是 BeanDefinition（元数据，还没实例化），BeanPostProcessor 操作的是 Bean 实例（已经 new 出来了）。前者改"图纸"，后者改"成品"。

三、事务的传播机制

REQUIRED 同生共死，REQUIRES_NEW 互不影响，NESTED 局部自治。

传播行为口诀含义
REQUIRED有我就加入，没有我就建。同生共死（一起回滚）有事务就加入，没有就新建；与外层事务一起回滚
REQUIRES_NEW不管有没有，我都要自己开。你是你，我是我（互不影响）总是新建事务，外层事务挂起；内外互不影响
NESTED我要做你儿子，我回滚不影响你，但你回滚我得死。局部自治（可局部回滚）嵌套事务，子事务可独立回滚（保存点），但外层回滚子事务也回滚

补充：REQUIRES_NEW 和 NESTED 都能"局部回滚"，但机制不同。REQUIRES_NEW 是完全独立的新事务（外层挂起），NESTED 是嵌套子事务（基于保存点，外层回滚子事务也回滚）。

四、事务的隔离级别

MySQL 默认 RR 解幻读，大厂常用 RC 高并发。

隔离级别说明
READ UNCOMMITTED（读未提交）最低隔离，有脏读风险，千万别用
READ COMMITTED（读已提交）解决脏读，但有不可重复读；互联网大厂常用
REPEATABLE READ（可重复读）解决不可重复读，MySQL 默认
SERIALIZABLE（串行化）最高隔离，性能灾难，千万别用

关键加分点：虽然 SQL 标准说 REPEATABLE READ 允许幻读，但 MySQL 的 InnoDB 通过间隙锁（Gap Lock）+ MVCC，在 RR 级别下已经能完全解决幻读。因此 MySQL 默认的 RR 实际上达到了接近串行化的一致性，并发性能却好得多。

选型适用场景原因
MySQL 默认 RR金融、交易等强一致性场景间隙锁 + MVCC 解决幻读，接近串行化
互联网大厂常用 RC高并发互联网业务RC 没有间隙锁，锁竞争更少，并发吞吐量更高；代价是允许不可重复读（通常业务能接受）
千万别用READ UNCOMMITTED、SERIALIZABLE脏读风险 / 性能灾难

五、Spring 如何解决 Bean 的循环依赖

三级缓存：成品、半成品、ObjectFactory 工厂。

三级缓存解决循环依赖，核心是"半成品提前暴露"。

缓存层级名称存放内容
一级缓存singletonObjects存放成品，即完全初始化好的单例 Bean
二级缓存earlySingletonObjects存放半成品，即已实例化但未完全初始化，被提前暴露出来供其他 Bean 依赖的引用
三级缓存singletonFactories存放工厂（ObjectFactory），其 getObject() 方法封装了生成最终被暴露的引用（原始对象或 AOP 代理对象）的逻辑

当出现循环依赖时，Bean A 通过三级缓存的工厂，在被依赖的那一刻才决定要暴露原始对象还是代理对象，从而解决了 AOP 代理与循环依赖共存的问题。三级缓存确保了 AOP 代理在循环依赖场景下也能被正确创建和注入。

补充：三级缓存不是为了"三级"，而是为了延迟决定暴露原始对象还是代理对象。如果没有 AOP，二级缓存就够了；三级缓存的 ObjectFactory 在被调用时才决定生成原始对象还是代理，保证循环依赖下 AOP 代理也能正确注入。

六、Spring Boot 自动配置原理

注解组合 → 选择器读配置 → 条件注解按需加载。

步骤发生什么
1核心注解 @SpringBootApplication 组合了 @EnableAutoConfiguration
2@EnableAutoConfiguration 通过 @Import(AutoConfigurationImportSelector.class) 导入选择器
3选择器读取所有 Jar 包中 META-INF/spring.factories 或 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports（Spring Boot 2.7+）文件里的配置类全路径
4加载这些配置类时，配合 @ConditionalOnClass（类路径存在某类）、@ConditionalOnMissingBean（容器无某 Bean）等条件注解，按需加载

补充（踩坑经验）：我曾经排包冲突，发现引入的第三方的 RedisAutoConfiguration 覆盖了默认的，导致连接池报错。解决方法是 @SpringBootApplication(exclude = RedisAutoConfiguration.class) 手动排除它。自动配置不是"全量加载"，而是"按需加载"——条件注解决定哪些配置类生效。

七、面试串联话术

事件→扩展点→事务→循环依赖→自动配置一气呵成。

Spring 事件驱动用 ApplicationListener，在单体应用内做模块解耦，极轻量无依赖；跨服务异步才用 MQ。

Bean 扩展点三剑客：BeanFactoryPostProcessor 改 BeanDefinition（图纸），BeanPostProcessor 改 Bean 实例（成品，AOP 代理用它），ApplicationContextAware 获取容器资源。需要替换整个 Bean 或动态加接口必须用 BeanPostProcessor，方法加日志用 @Aspect 就够。

事务传播 REQUIRED 同生共死、REQUIRES_NEW 互不影响、NESTED 局部自治；隔离级别 MySQL 默认 RR（间隙锁+MVCC 解幻读），大厂常用 RC 高并发。循环依赖靠三级缓存——一级成品、二级半成品、三级 ObjectFactory 工厂延迟决定原始还是代理。

Spring Boot 自动配置是 @SpringBootApplication → @EnableAutoConfiguration → AutoConfigurationImportSelector 读 spring.factories → @Conditional 按需加载，不是全量加载。
