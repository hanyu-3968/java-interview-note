单机分布式一体化 + Paxos 强一致 + LSM-Tree 高压缩 + 兼容 MySQL。

一、OceanBase 是什么

蚂蚁自研原生分布式库，一套内核两种部署。

蚂蚁集团 2010 年自研的原生分布式数据库，核心设计理念是单机分布式一体化——一套内核代码同时支持集中式单机和分布式集群部署。

  • 经历淘宝双十一超大规模并发和金融行业核心系统考验
  • 打破"集中式或分布式二选一"界限，可从小规模单机起步，业务增长后无需修改代码平滑扩容成分布式集群
  • 一套系统同时处理事务处理（TP）、实时分析（AP）甚至 AI 应用

补充："单机分布式一体化"是同一套内核两种部署形态，不是两套代码；也不是在 MySQL 上加代理层的分布式中间件方案，OB 是原生分布式数据库。

二、核心组件与架构

三大组件 + Shared-Nothing + LSM-Tree + Paxos。

三大核心组件

组件定位核心职责
OBServer 最核心进程 每台服务器一个 observer 进程，集成 SQL 引擎、事务引擎、存储引擎，负责节点间通信和负载均衡
Zone 可用区（逻辑概念） 通常对应一个机房或可用区，一个集群多 Zone，数据副本分布在不同 Zone 实现机房级容灾
Tenant 租户（资源隔离单位） 逻辑上是一个独立数据库实例，拥有独立 CPU/内存/IO，多租户整合小库提升资源利用率

系统架构四层

层机制关键能力
整体架构 Shared-Nothing 无共享 节点间完全对等，无单点瓶颈
存储层 LSM-Tree 数据先写内存 MemTable，达阈值转储为只读 SSTable，列存编码 + 通用压缩，存储成本省 70%~90%
复制层 Paxos 共识协议 多副本同步 Redo 日志，每分区一个 Leader 读写 + 多个 Follower 备份，Leader 故障 RTO<8s、RPO=0
SQL 层 解析→优化→执行 Parser→Resolver→Transformer→Optimizer→代码生成→Executor，支持本地/远程/分布式三种执行计划，带 Plan Cache

补充：Zone 是物理/机房维度的容灾单元，Tenant 是逻辑/资源维度的隔离单元，二者正交——一个 Tenant 的数据副本会分布在多个 Zone。MemTable 在内存可写，SSTable 在磁盘只读，转储后靠合并（Compaction）清理旧版本。

三、相比 MySQL 的六大优点

架构/高可用/HTAP/存储/多租户/兼容性全面领先。

维度OceanBaseMySQL
架构 原生分布式，水平扩展对应用透明 集中式，大规模扩展靠分库分表，对应用不透明、运维复杂
高可用 Paxos 原生多副本，RPO=0、RTO<8s，支持城市级故障自动恢复 依赖主从复制 + 故障切换，通常需人工介入，存在数据丢失风险
混合负载 HTAP 一套系统同时支持高并发 TP 和复杂实时 AP，无需数据搬迁 分析能力弱，通常需同步到单独 AP 系统
存储成本 LSM-Tree + 高效压缩，存储成本降 70%~90% InnoDB 压缩比相对较低，存储成本更高
多租户 原生支持，资源隔离好，可整合多个数据库实例 无原生多租户概念
兼容性 高度兼容 MySQL 5.7/8.0 语法和协议，迁移改造成本低 —

补充：RPO=0 表示零数据丢失，RTO<8s 表示 8 秒内恢复服务，两个指标衡量不同维度。HTAP 是一套引擎一套数据同时跑 TP 和 AP，不是 TP 库同步到 AP 库的 ETL 方案。

四、如何从 MySQL 迁移到 OceanBase

OMS 四阶段，应用层只改配置不改代码。

核心工具是 OceanBase 迁移服务（OMS），支持不停机或极短停机的平滑迁移。

迁移四阶段

阶段名称关键动作易踩坑点
一 前期评估与准备 检查表结构（每表必须有显式主键）；梳理视图/触发器/存储过程/外键；确认 utf8mb4 和 sql_mode 一致 无主键表性能急剧下降
二 应用层最小化改造 仅改配置，不修改 Java 业务逻辑和 SQL；替换 JDBC 驱动；改连接 URL 和用户名格式 用户名格式特殊
三 数据迁移实操 中小规模停机用 mysqldump 导出 + obclient 导入；海量数据或零停机用 OMS 全量 + 增量 + 无缝切换 选错工具导致停机过长
四 验证与上线 数据一致性校验、业务回归测试、正式上线切换连接地址 跳过校验直接上线

连接配置改造细节

项MySQL 原配置OB 方案 A（推荐）OB 方案 B
JDBC 驱动 mysql-connector-java mysql-connector-java（不变） oceanbase-client
URL 前缀 jdbc:mysql:// jdbc:mysql://（不变） jdbc:oceanbase://
用户名 root root@my_tenant#obtest root@my_tenant#obtest

用户名格式：用户名@租户名#集群名，如 root@my_tenant#obtest。

补充：方案 A 沿用 MySQL 驱动、URL 不变，改造成本最低，推荐；方案 B 用官方驱动性能更优但需改 URL 前缀。"无主键表必须补主键"不是 OB 限制不能建表，而是无主键表在分布式环境下性能急剧下降，迁移前必须补上。

五、面试回答模板

三句话讲清 OceanBase 是什么、机制、实战。

问题本质是：OceanBase 是蚂蚁自研的原生分布式数据库，采用单机分布式一体化架构，高度兼容 MySQL 和 Oracle，一套系统同时支持 TP 和 AP。

机制是：三大组件 OBServer/Zone/Tenant + Shared-Nothing 架构，存储用 LSM-Tree 高压缩（省 70%~90%），复制用 Paxos 多副本强一致（RPO=0、RTO<8s 自动选主）。

实战中我会：从 MySQL 迁移走 OMS 四阶段——前期补主键、应用层只改驱动配置、数据用 mysqldump 或 OMS 迁移、最后校验上线，业务代码零修改。
