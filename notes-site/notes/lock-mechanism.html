synchronized 锁升级四阶段 + MySQL 行表锁 + ReentrantLock AQS。

一、synchronized 原理：Monitor 是底层基石

对象关联 Monitor，monitorenter 进 monitorexit 出。

synchronized 底层依赖 JVM Monitor（管程/监视器）锁机制。字节码层面，同步块通过 monitorenter 和 monitorexit 两条指令实现。

  • 每个 Java 对象都关联一个 Monitor，对象头 Mark Word 存锁状态
  • 线程通过获取 Monitor 持有权来加锁：成功进入同步块，失败阻塞
  • monitorexit 出现两次（正常退出 + 异常退出），保证锁一定释放

补充：同步方法没有 monitorenter/monitorexit 指令，而是在方法表 flags 里设 ACC_SYNCHRONIZED 标志，JVM 调用时自动加锁解锁。

二、synchronized 锁升级：四阶段逐级加重

无锁→偏向→轻量级→重量级，升级不可逆。

阶段触发条件实现机制性能记忆画面
无锁 初始状态 对象头无锁标记 最快 空房间没人占
偏向锁 单线程访问 Mark Word 记线程 ID，零开销进入 极快 门牌写你名字，直接进
轻量级锁 第二线程申请（非同时竞争） CAS 自旋 + 栈帧锁记录 快 一前一后来，敲门没人就进
重量级锁 多线程同时竞争且自旋失败 Monitor 阻塞，OS 调度唤醒 慢 排队取号，叫号才进

补充：轻量级锁触发是"第二个线程申请锁"，不是两个线程同时竞争——可以一前一后交替执行同步块；自旋锁不是独立阶段，是轻量级到重量级之间的过渡策略。JDK15 起偏向锁默认关闭（-XX:-UseBiasedLocking），JDK18 逐步废弃。

三、MySQL 锁：行锁与表锁的取舍

行锁并发高开销大，表锁并发低开销小。

维度行锁表锁记忆画面
锁定粒度 整行数据 整张表 行锁锁一排座位，表锁锁整个厅
开销/加锁速度 大 / 慢 小 / 快 行锁要定位行，表锁一把抓
锁冲突概率 最低 最高 行锁只冲突同行
并发度 最高 最低 行锁让不同行并行
引擎支持 InnoDB MyISAM / InnoDB MyISAM 只支持表锁

补充：InnoDB 既支持行锁也支持表锁，默认行锁；但未走索引的查询会退化为表锁（行锁基于索引实现）。MyISAM 只支持表锁。

悲观锁 vs 乐观锁

维度悲观锁乐观锁记忆画面
思路 拿数据就上锁，别人 block 拿数据不上锁，更新时校验 悲观先占座，乐观提交时看
实现 SELECT ... FOR UPDATE 版本号 / CAS 机制 悲观靠 DB 锁，乐观靠应用层
冲突假设 冲突频繁 冲突稀少 悲观适合写多，乐观适合读多

补充：共享锁（S 锁）是悲观锁的一种——多个事务对同一资源共享同一把锁（读锁），允许并发读但阻塞写。乐观锁不是"不加锁"，而是延迟到更新时校验，本质是应用层策略。

四、公平锁与非公平锁：顺序 vs 吞吐

公平 FIFO 排队，非公平插队抢吞吐。

维度公平锁非公平锁记忆画面
获取顺序 按等待顺序，FIFO 队头取 不管顺序，概率相等 公平排队取号，非公平谁手快谁得
性能 低，大量时间花在调度 高，响应速度快 公平要切换线程，非公平可连续获取
饥饿 不会饿死 可能饿死等待久的线程 公平保底，非公平看运气
默认 需显式配置 ReentrantLock / synchronized 默认 new ReentrantLock(true) 才公平

补充：synchronized 是非公平锁且不可配置；ReentrantLock 默认非公平，可通过构造参数 new ReentrantLock(true) 切换为公平。非公平吞吐高是因为允许"刚释放锁的线程立即再抢"，减少线程切换开销。

五、可重入锁与 ReentrantLock：state 计数实现重入

可重入靠 state 累加，同一线程多次获取不死锁。

机制作用记忆画面
state 计数 记录重入次数 计数器：进一次 +1，出一次 -1
线程 ID 记录 判断是否同一线程 门牌记住户，住户可反复进出
state > 0 锁仍被持有 计数器没归零，门还锁着
state = 0 完全释放 计数器归零，门开了

ReentrantLock 基于 AQS（AbstractQueuedSynchronizer）实现：

  • 加锁：通过 currentThread == exclusiveOwnerThread 判断可重入性，同一线程则 state 累加，否则入队等待
  • 解锁：state 减到 0 才完全释放，此前 state > 0 锁仍被持有
  • 手动释放：必须在 finally 块中调用 unlock()，否则死锁

补充：synchronized 是 JVM 层面自动释放（monitorexit），ReentrantLock 是 API 层面手动释放，忘记 unlock 会死锁。两者都可重入。ReentrantLock 比 synchronized 多了：可中断（lockInterruptibly）、可超时（tryLock）、可公平、多条件变量（Condition）。

高频场景题

三道诊断题，先判断再答机制。

"synchronized 和 ReentrantLock 怎么选？"

先看是否需要高级特性——需要可中断、超时、公平、多 Condition 选 ReentrantLock；简单互斥选 synchronized（JVM 自动释放、锁升级优化、JDK6 后性能差距很小）。synchronized 用法简单不会忘释放，ReentrantLock 灵活但易漏 unlock。

"InnoDB 行锁为什么有时变表锁？"

先看 SQL 是否走了索引——InnoDB 行锁基于索引实现，WHERE 条件未命中索引（或类型不匹配导致索引失效）时，行锁退化为表锁。排查：EXPLAIN 看是否 type=ALL 全表扫描，加合适索引即可恢复行锁。

"偏向锁为什么 JDK15 后默认关闭？"

先看收益与成本——偏向锁对单线程场景收益大，但现代应用多线程竞争普遍，偏向锁在竞争时撤销开销高（STW），且维护复杂。JDK15+ 优化后轻量级锁 CAS 足够快，偏向锁收益下降，故默认关闭。

最后复习：闭眼回忆 8 句

原理、升级、行表锁、悲观乐观、公平、可重入、AQS。

  1. 原理：synchronized 底层靠 Monitor，同步块用 monitorenter/monitorexit，同步方法用 ACC_SYNCHRONIZED 标志。
  2. 升级：无锁→偏向（单线程）→轻量级（CAS 自旋）→重量级（Monitor 阻塞），单向不可逆。
  3. 易混：轻量级是"第二线程申请"非"同时竞争"；自旋锁是过渡，不是独立阶段。
  4. MySQL 行/表锁：行锁开销大并发高（InnoDB 默认），表锁开销小并发低（MyISAM）；InnoDB 未走索引退化为表锁。
  5. 悲观/乐观：悲观先锁（FOR UPDATE），乐观靠版本号校验；共享锁是悲观锁的一种。
  6. 公平/非公平：公平 FIFO 不饿但慢，非公平插队快但可能饿死；synchronized 永远非公平，ReentrantLock 默认非公平可配置。
  7. 可重入：靠 state +1/-1 计数 + 线程 ID 判断，归零才完全释放；synchronized 和 ReentrantLock 都可重入。
  8. AQS：ReentrantLock 基于 AQS，currentThread==exclusiveOwnerThread 判重入，必须 finally 手动 unlock。
