注册发现 + 声明式调用 + 熔断降级 + 网关，微服务全家桶。

一、SpringCloud 是什么

微服务治理平台，基于 SpringBoot 的全套分布式方案。

SpringCloud 是一个服务治理平台，提供服务注册与发现、配置中心、消息中心、负载均衡、数据监控等一整套分布式系统解决方案，基于 SpringBoot 实现。

  • 对比 Dubbo：Dubbo 是 RPC 框架只解决"服务间调用"；SpringCloud 提供全套分布式方案。
  • 不是单一框架，而是组件统称（Netflix 体系 + Spring 自研 + 阿里 Sentinel/Nacos 等）。

补充：SpringCloud Alibaba 是兼容 SpringCloud 规范的另一套实现（Nacos/Sentinel/Seata），不是替代整个 SpringCloud，而是替换其中的注册中心、配置中心、容错组件。

二、常用组件全景

注册 Eureka、均衡 Ribbon、容错 Hystrix、调用 Feign、网关 Gateway。

组件职责一句话定位记忆画面
Eureka服务注册中心服务登记 + 发现户籍管理处
Ribbon客户端负载均衡多实例挑一个调用食堂多窗口排队
Hystrix服务容错保护熔断降级防雪崩保险丝跳闸

补充：Feign 与 OpenFeign 不是两个独立产品。OpenFeign 是 SpringCloud 在 Feign 基础上支持 SpringMVC 注解的增强版，现在说 Feign 一般就指 OpenFeign。

三、Eureka 注册中心

AP 模型 + 心跳判活 + 自我保护 + 客户端缓存。

Eureka 采用 AP 模式（高可用优先于强一致），核心机制四件套：

机制原理作用记忆画面
心跳机制提供者定期发心跳，超时未收到则注销判活定时打卡
自我保护短时间大量失心跳时启动，不再剔除实例防网络抖动误删宁可错留不杀
客户端缓存消费者本地缓存注册表Eureka 全挂仍能调用备用通讯录
高可用多节点互相注册，请求失败自动切换单点不瘫多个办事处

补充：Eureka 自我保护 vs ZooKeeper leader 选举——Eureka 网络分区时保留疑似宕机节点（AP）；ZooKeeper master 失联时重新选举 30~120 秒，选举期整个集群不可用（CP）。这是注册中心选 Eureka 而非 ZK 的关键理由。

四、Consul 注册中心

CP 模式 + 主动健康检查 + 一站式服务治理。

Consul 基于 Go 语言开发，单可执行文件部署，与 Docker 无缝配合。流程：提供者启动 → 向 Consul 注册 IP/端口 → Consul 每 10s 主动发健康检查（HTTP/TCP/脚本）→ 消费者从临时表任选一个 IP 调用。

维度EurekaConsul记忆钩子
核心定位纯服务注册发现一站式服务网格（发现+配置+健康）单一 vs 全能
CAP 模型AP（高可用优先）CP（强一致优先）宁脏不停 vs 宁停不脏
健康检查客户端心跳上报服务端主动探测被动打卡 vs 主动体检
配置中心不支持内置分布式 KV 存储Consul 顺带管配置
多语言仅 JavaHTTP/DNS API 多语言Consul 跨语言
管理界面基础功能丰富 Web UIConsul 自带仪表盘
项目状态维护模式（停更）活跃开发Eureka 退休，Consul 当红

补充：从 Eureka 到 Consul 不是"换个注册中心"，而是从"服务发现工具"升级到"服务治理平台"——多出配置中心、多语言支持、主动健康检查。面试答出"AP vs CP"和"被动心跳 vs 主动探测"两条即可。

五、OpenFeign 声明式调用

动态代理 + SpringMVC 注解，像调本地方法调远程。

Feign 是声明式、模板化的 HTTP 客户端，封装 Ribbon + RestTemplate，实现面向接口编程：只需创建接口加注解，即可像调本地方法一样调远程。

对比项FeignOpenFeign记忆点
注解支持Feign 自带注解支持 SpringMVC 注解OpenFeign 更 Spring
动态代理有有，解析 @RequestMapping 生成实现类同机制
负载均衡内置 Ribbon内置 Ribbon同
SpringCloud 主推旧新，推荐使用用 OpenFeign

OpenFeign 使用四步：

  1. 消费者添加 spring-cloud-starter-openfeign 依赖。
  2. 业务层接口加 @FeignClient(name="服务名") 声明调用目标。
  3. 抽象方法用 SpringMVC 注解（@GetMapping/@PostMapping）配置路径与参数。
  4. 启动类加 @EnableFeignClients 激活 Feign 组件。

补充：OpenFeign 的"像调本地方法"是动态代理实现的，不是真的本地调用——底层仍是 HTTP 请求，网络失败会抛异常，所以必须配合 Hystrix/Sentinel 做降级。@FeignClient 的 name 要与注册中心服务名一致。

六、Hystrix 四大容错机制

资源隔离 + 熔断 + 降级 + 缓存，防雪崩基石。

Hystrix 通过四大机制防止单服务故障引发整个系统雪崩：

机制核心逻辑适用场景记忆画面
资源隔离线程池/信号量隔离，限制故障传播依赖服务多、需互不影响一人一房间
熔断器失败率达阈值自动断开，直接走降级服务持续失败保险丝跳闸
服务降级失败/超时/熔断时执行 fallback 备选方案兜底返回友好提示备用方案
请求缓存同上下文重复请求走缓存减少重复网络开销备忘录

6.1 资源隔离两种方式

方式原理优点缺点记忆画面
线程池隔离每个依赖服务独立线程池（支付/库存各一个）故障不蔓延、最稳线程切换开销、占资源独立小房间
信号量隔离计数器限并发请求数轻量、无切换不适合网络延迟场景门口限流牌

补充：线程池隔离有切换开销但隔离最彻底（推荐给可能网络延迟的服务）；信号量隔离轻量但隔离弱（推荐给内部纯计算、无网络调用的服务）。不是"信号量更好"，而是看场景。

6.2 熔断器三态流转

  • Closed（关闭）：正常调用，统计失败率。
  • Open（打开）：失败率达阈值（如 10 秒内 20 请求且 50% 失败）→ 自动断开，所有请求直接走降级。
  • Half-Open（半开）：一段时间后放少量请求探测，成功则关闭恢复，失败则继续打开。

补充：降级 ≠ 熔断。熔断是自动切断（机制），降级是返回备选（结果）。熔断打开会触发降级，但降级也会在普通超时/异常时单独触发——降级范围更广。

七、Sentinel 服务哨兵

以流量为切入点，流控+熔断+降级+负载保护，替代 Hystrix。

Sentinel 是阿里开源的高性能、轻量级流量控制组件，可替代 Hystrix。

对比项HystrixSentinel记忆点
切入点资源隔离为主以流量为切入点Sentinel 抓流量
维度隔离+熔断+降级+缓存流控+熔断降级+系统负载保护Sentinel 多一维
配置代码硬编码控制台动态规则实时推送Sentinel 可视化
状态维护模式活跃用 Sentinel

八、网关服务

系统唯一入口，路由+鉴权+限流+监控，推荐 Gateway。

网关是系统对外的唯一入口，隔离外部访问与内部微服务。客户端请求先到网关，网关根据请求标识判断具体微服务地址再转发。

职责作用记忆画面
动态路由按请求标识转发到具体微服务快递分拣
负载均衡多实例挑一个多窗口排队
身份认证统一鉴权，下游免重复校验大门保安查证
安全审查限流、黑白名单安检
监控统计统一埋点门禁日志
缓存/静态响应减少下游压力前台备传单
方案实现方式特点记忆点
Nginx + Lua服务器层负载均衡高性能、配置式老牌门神
ZuulRibbon + Eureka 实现负载均衡Netflix 旧方案、阻塞式已过气
SpringCloudGatewayFilter 链 + WebFlux非阻塞、统一 API 路由推荐新选型

补充：Nginx 负载均衡是服务器层（按 IP/域名转发），Zuul/Gateway 负载均衡是应用层（靠 Ribbon+Eureka 按服务名转发）。SpringCloudGateway 用 WebFlux 非阻塞模型，性能优于 Zuul 的阻塞模型，是 Zuul 的官方替代。

九、高频场景题

超时定位、自我保护、Feign 404 三类诊断。

"服务调用超时，怎么定位是网络、服务还是熔断？"

先看 Hystrix 日志是否有 short-circuited（熔断打开）或 timeout（超时）——有熔断说明下游持续失败已触发熔断器，查下游服务健康；有超时但无熔断，调大 feign.client.config.default.connectTimeout/readTimeout 并排查下游 RT；两者都没有则查网络链路（ping/telnet 注册中心与服务实例）。

"Eureka 自我保护模式触发了，要不要紧？"

不要紧，反而是设计如此。自我保护在"短时间内大量心跳丢失"时启动，保留疑似宕机实例避免网络抖动误删。处理方式：确认是否真网络分区，网络恢复后会自动退出；若确实有实例下线，需手动清理或等心跳恢复。强行关闭（eureka.server.enable-self-preservation=false）反而可能在网络抖动时误删健康实例。

"OpenFeign 调用报 404，但服务明明注册了？"

九成是 @FeignClient 的 name 与注册中心服务名不一致，或接口上的 @RequestMapping 路径与提供者 Controller 路径不匹配。先在 Eureka/Consul 控制台核对服务名，再比对 Feign 接口注解路径与提供者 @RestController 路径是否完全一致（包括 @PathVariable/@RequestParam 参数名）。

十、面试回答模板

本质是哪一层 → 机制+取舍 → 实战选型配置。

问题本质是……（先说 SpringCloud 问的是哪一层：注册中心、调用、容错、还是网关）。

机制是……（解释原理 + 关键组件），因为……（为什么这样设计，AP/CP 取舍、防雪崩等）。

实战中我会……（选型 + 配置），例如……（Eureka vs Consul、Hystrix vs Sentinel、Gateway vs Zuul）。

例：问"为什么用 Eureka 不用 ZooKeeper 做注册中心"——本质是注册中心的 CAP 取舍；机制上 Eureka 是 AP 模型，网络分区时保留所有实例保证可用，ZooKeeper 是 CP 模型，master 失联要 30~120 秒选举，选举期整个集群不可用；实战中我会选 Eureka/Consul 按业务对"可用 vs 一致"的偏好定，微服务场景一般可用性优先所以 Eureka 更合适，配合客户端缓存即使注册中心全挂也能短期调用。

十一、最后复习：闭眼回忆 8 句

定位、组件、Eureka、Consul、Feign、Hystrix、Sentinel、网关。

  1. 定位：SpringCloud 是微服务治理全家桶，对比 Dubbo（仅 RPC）提供全套分布式方案，基于 SpringBoot。
  2. 组件：Eureka 注册、Ribbon 均衡、Hystrix 容错、Feign/OpenFeign 调用、Zuul/Gateway 网关。
  3. Eureka：AP 模型 + 心跳判活 + 自我保护防误删 + 客户端缓存兜底 + 多节点高可用。
  4. Consul：CP 模型 + 主动健康检查（每 10s）+ KV 配置中心 + 多语言 + Web UI，活跃开发；Eureka 已维护模式。
  5. OpenFeign：动态代理 + SpringMVC 注解 + 内置 Ribbon，四步用：依赖、@FeignClient、@RequestMapping、@EnableFeignClients。
  6. Hystrix 四机制：资源隔离（线程池/信号量）、熔断（Closed/Open/Half-Open 三态）、降级（fallback）、缓存。
  7. Sentinel：以流量为切入点，流控+熔断+降级+系统负载保护，控制台动态规则，替代 Hystrix。
  8. 网关：唯一入口做路由/鉴权/限流/监控；Nginx+Lua 服务器层 vs Zuul/Gateway 应用层，推荐 SpringCloudGateway（WebFlux 非阻塞）。

十二、怎么练才记得住

遮表自讲、场景题口述、换项目举例、默写总图。

  1. 每次只看一个组件，遮住表格，先自己说出"职责 → 机制 → 易混点 → 适用场景"，再对照。
  2. 用"高频场景题"的 3 道题各讲 30 秒；卡住时只回看对应小节。

  4. 复习时轮流画"微服务全链路总图"和"Eureka vs Consul 对比表"；能默写出四大容错机制和熔断三态才算熟。
