一、Jedis vs Redisson：怎么选客户端

轻量命令用 Jedis，分布式协调用 Redisson

Redis 客户端两大选择：Jedis 是轻量 Redis 客户端，Redisson 是分布式 Java 数据结构框架。选型看业务复杂度与可靠性要求。

维度JedisRedisson
定位轻量 Redis 客户端分布式 Java 数据结构框架
适用场景只需 SET/GET 等基本命令、对延迟敏感需分布式锁协调多节点、把 Redis 当 Java Map/List/Queue 用
连接管理连接池管理，需自己保证线程安全内置连接池，API 天然线程安全
分布式锁手写 setNx 脚本RLock 开箱即用，带看门狗/可重入
命令脚本手动维护 Lua 脚本封装常用数据结构，免写脚本

补充：低并发非核心业务、锁操作极短可用 Jedis setNx；高并发核心业务（订单/扣库存）生产级可靠性用 Redisson。

二、setNx 四大问题与 Redisson 解法

看门狗续期·计数器重入·等待超时·集群策略

裸 setNx 有四个坑，Redisson 用看门狗 + 计数器 + 等待超时 + 集群策略逐一填平。

问题现象Redisson 解法
① 锁过期并发线程超过锁过期时间还在跑，锁已释放，另一线程拿到锁看门狗自动续期
② 无法自动续期任务执行中锁到期不能延续看门狗定时任务周期续期
③ 不可重入同线程在方法 A 拿锁调用方法 B 再拿同一把锁，被自己阻塞死锁内部计数器，同线程可多次加锁
④ 主从切换丢锁主节点宕机，从节点升级时锁数据可能丢失，两客户端同时持锁集群模式多种策略应对主从切换

补充：看门狗不是无限续期——它依赖业务线程存活，若业务线程卡死，看门狗会一直续期导致锁永不释放，仍要给业务设超时兜底。

三、RDB vs AOF：两种持久化怎么取舍

RDB 拍照丢一截，AOF 录像更安全

Redis 持久化两套方案：RDB 全量内存快照，AOF 追加写命令日志。

维度RDBAOF
原理整个拷贝内存快照把写操作命令持续写到日志文件
数据安全可能损失一部分数据几乎不丢（按刷盘策略）
文件体积小（压缩二进制）大（命令文本）
恢复速度快（直接载入）慢（重放命令）
适用场景容忍少量丢失、追求恢复速度数据安全要求高

补充：Redis 的 RDB/AOF ≠ MySQL 的 redo/undo log。redo log 记变更后的新数据实现持久性，undo log 记变更前的旧数据实现原子性和 MVCC，二者属于 InnoDB 事务日志；RDB/AOF 是 Redis 为重启恢复做的持久化，不是事务日志。

四、缓存三大问题：穿透、击穿、雪崩

穿透查假·击穿热点失效·雪崩集体失效

缓存失效三连，区分关键看"数据存不存在"和"失效范围"。

问题触发原因解决方案
缓存穿透黑客故意请求缓存中不存在的数据，所有请求打到数据库接口层校验 / 布隆过滤器 / 维护合法 Key
缓存击穿热点 Key 被高并发访问突然失效，瞬间冲击数据库互斥锁 / 热点数据不过期 / 本地缓存
缓存雪崩缓存统一时间大面积失效，数据库瞬时压力陡增给失效时间加随机值避免集体失效

补充：穿透是数据根本不存在（缓存和库都没有），击穿是数据存在但缓存刚好失效（库里有），雪崩是大面积 Key 集体失效。三者解法不同，别混答。

五、过期键删除策略：惰性 vs 定期

惰性省 CPU，定期省内存，Redis 组合用

策略时机优点缺点
惰性过期访问 Key 时才判断是否过期节省 CPU对内存不友好，可能大量过期 Key 占用内存
定期过期每隔一段时间扫描一定数量 Key 清除已过期的折中，主动回收内存有扫描开销

补充：Redis 实际是惰性 + 定期组合使用，单用惰性会导致不被访问的过期 Key 一直占内存。

六、主从复制与哨兵：高可用两件套

主从 sync 抄 rdb，哨兵监控自动换岗

机制解决问题工作流程
主从复制数据备份 + 读写分离slave 向 master 发 sync → master 后台子进程把数据快照保存到数据文件发给 slave → slave 接收 .rdb 保存到本地载入内存完成同步
哨兵 Sentinel主节点宕机自动故障转移不断监控主从节点运行状态，主不能工作时将一个从升级为新主；通过配置文件发现主服务器，再通过 info 发现从服务器

补充：主从复制只是数据同步，主挂了不会自动切换；哨兵才是自动故障转移的指挥官。没有哨兵的主从，主挂了要人工介入。

面试回答模板

问题本质是：Redis 分布式锁的可靠性，核心矛盾是"锁过期但任务没跑完"和"主从切换丢锁"。

机制是：Redisson 用看门狗定时续期解决锁过期，用内部计数器实现可重入，用集群多策略应对主从切换；裸 setNx 这四点都得自己写脚本，生产级难保证。

实战中我会：核心业务（订单/扣库存）直接上 Redisson RLock，配合业务超时兜底；非核心轻量场景才用 Jedis setNx，并自己加 Lua 脚本保证原子性。

最后复习：闭眼回忆 8 句

  1. Jedis 轻量基本命令，Redisson 分布式协调，核心业务上 Redisson。
  2. setNx 四大坑：锁过期并发、无法续期、不可重入、主从切换丢锁。
  3. Redisson 解法：看门狗续期、计数器可重入、等待超时、集群多策略。
  4. RDB 全量快照可能丢数据恢复快，AOF 追加命令日志更安全恢复慢。
  5. Redis 的 RDB/AOF 不是事务日志，和 InnoDB 的 redo/undo 不是一回事。
  6. 穿透查假用布隆过滤器，击穿热点加锁或不过期，雪崩集体加随机过期值。
  7. 过期策略惰性 + 定期组合用，单用惰性会内存堆积。
  8. 主从复制 sync 抄 .rdb，哨兵监控自动故障转移，发现从服务器靠 info。
