线程池复用是根因，五大坑各有修复手段。

一、线程安全：ThreadLocal 与 ConcurrentHashMap

ThreadLocal 要 remove，批量操作要原子。

Web 服务器（如 Tomcat）用线程池复用线程处理请求，没有显式 new Thread 也会有线程安全问题——线程创建昂贵，请求结束后线程不销毁，会被下一个请求复用。

坑点触发条件后果修复
ThreadLocal 未 remove Tomcat 线程池复用线程，请求结束后 ThreadLocal 残留 下个请求读到上个请求数据，串号/越权/内存泄漏 try-finally 中显式 threadLocal.remove()
ConcurrentHashMap 批量非原子 putAll 等批量操作在并发下被其他线程穿插 批量过程非原子，部分写入被覆盖，配置不一致 逐 key 用 replaceAll/compute，或显式 synchronized

补充：ConcurrentHashMap 的单个 put/compute 是原子的，但 putAll、先 get 后 put 这类"复合操作"不是原子的。线程安全容器 ≠ 所有操作都原子。

二、加锁问题：粒度、读写与公平锁

粒度小、级别对、读写分、公平锁别乱开。

维度考量点选择
锁粒度 只为必要代码块加锁，降低锁范围 锁代码块而非整个方法
锁级别 共享资源是类级别还是实例级别 类资源锁 Class，实例资源锁 this 或具体对象
读写场景 读写比例差异明显时 ReentrantReadWriteLock 区分读写锁
悲观/乐观 访问冲突激烈还是稀疏 激烈用悲观锁（synchronized），稀疏用乐观锁（CAS）

ReentrantLock 和 ReentrantReadWriteLock 都提供公平锁版本（构造传 true），但任务竞争强时开启公平锁会让性能下降上百倍，没有明确需要不要轻易开启。

补充：synchronized 加锁时要弄清共享资源是类级别还是实例级别、会被哪些线程操作；加锁要尽可能只为必要代码块加锁，降低锁粒度。

三、HTTP 调用：Feign 超时与重试坑

超时连读一起配，以 Feign 为准，重试按需关。

网络不稳定，超时重试是双刃剑——重试前必须确认服务端接口幂等。SpringCloud 用 Feign 声明式调用，SpringBoot 可能直接用 Apache HttpClient。

坑点默认/现象修复
读取超时太短 默认 ReadTimeout=1s 按接口耗时调大
超时配置不生效 只配 readTimeout 不配 connectTimeout 必须同时配连接超时和读取超时
Feign 与 Ribbon 冲突 同时配置时以 Feign 为准 统一在 Feign 侧配置
重试导致重复请求 Ribbon 默认自动重试 MaxAutoRetriesNextServer=0 禁止重试
并发连接数瓶颈 HttpClient/浏览器默认限制最大并发连接 高并发客户端调大连接池

补充：Feign 的超时和 Ribbon 的超时是两套配置，同时存在时以 Feign 为准；但 Ribbon 的重试是独立机制，禁重试要单独设 MaxAutoRetriesNextServer=0。超时归 Feign，重试归 Ribbon，别混。

四、事务生效：@Transactional 失效四场景

public + 外部代理调用 + 抛 RuntimeException 才完整。

Spring 默认通过动态代理实现 AOP 事务增强，绕过代理就失效。必须通过代理过的类从外部调用目标方法才能生效。

场景原因修复
非 public 方法 JDK 动态代理只能代理 public 方法，private 无法代理 事务方法必须 public
this 内部调用 this 是目标对象本身，不是代理对象，绕过 AOP 通过注入的代理 Bean 调用，或 AopContext.currentProxy()
CGLIB 代理 private CGLIB 通过继承生成子类，private 方法子类不可见 方法改 public
异常被吞/非 RuntimeException 默认只对 RuntimeException/Error 回滚 @Transactional(rollbackFor=Exception.class)

补充："事务生效"和"事务回滚"是两件事——生效看是否经过代理（public + 外部调用），回滚看抛的异常类型（默认只回滚 RuntimeException）。方法代理到了但抛了 checked 异常，事务生效却不回滚，照样提交。

高频场景题

串号查 ThreadLocal，超时查 Feign，内层事务查 this。

"接口偶发串号，用户 A 看到用户 B 的数据，怎么查？"
先确认是否用了 ThreadLocal 存用户信息且请求结束未 remove——Tomcat 线程池复用线程，上一个请求的用户信息残留。修复：在拦截器 afterCompletion 或 try-finally 中显式 threadLocal.remove()；压测高并发短请求可复现。

"Feign 调用偶发超时，但服务端日志显示处理很快，怎么查？"
大概率是 Feign 默认 ReadTimeout=1s 太短，或只配了 readTimeout 没配 connectTimeout 导致配置不生效。先看 Feign 配置是否同时配了连接和读取超时，再看是否与 Ribbon 冲突（以 Feign 为准），最后看客户端连接池是否打满。

"@Transactional 方法里调另一个 @Transactional 方法，内层事务没生效？"
典型 this 调用失效——内层方法通过 this.xxx() 调用，this 是目标对象不是代理对象，绕过了 AOP。修复：注入自身 Bean（@Autowired private XxxService self; 后 self.xxx()），或用 AopContext.currentProxy() 拿代理对象调用。

最后复习：闭眼回忆 8 句

根因、ThreadLocal、CHM、锁、公平锁、Feign、连接池、事务。

  1. 根因：Web 服务器用线程池复用线程，没显式 new Thread 也会有线程安全问题。
  2. ThreadLocal：用完必 remove()，放 try-finally 或拦截器 afterCompletion，否则线程复用串号。
  3. ConcurrentHashMap：单 key 原子，putAll/复合操作非原子；批量要逐 key compute 或显式加锁。
  4. 锁粒度：只锁必要代码块；区分类级别（锁 Class）和实例级别（锁 this）；读写差异大用 ReentrantReadWriteLock。
  5. 公平锁：ReentrantLock/ReentrantReadWriteLock 都有公平版本，竞争强时性能下降上百倍，勿轻易开。
  6. Feign：默认读取超时 1 秒；配超时必须连接+读取一起配；与 Ribbon 同时配以 Feign 为准；MaxAutoRetriesNextServer=0 禁重试。
  7. HTTP 客户端：HttpClient/浏览器都限制最大并发连接数，高并发客户端要调大连接池，否则吞吐瓶颈。
  8. @Transactional：public + 外部代理调用 + 抛 RuntimeException 才完整；非 public、this 调用、checked 异常都失效或不回滚，用 rollbackFor=Exception.class 兜底。
