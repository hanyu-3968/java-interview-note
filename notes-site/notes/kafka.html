分布式消息队列，高吞吐低延迟，三端全链路保可靠。

一、Kafka 是什么

消息缓冲池：生产者写，消费者读。

分布式消息队列，核心能力是高吞吐、低延迟的数据流处理。可以理解为一个消息缓冲池——生产者往里写，消费者从里读。

核心场景具体说明
解耦系统上下游通过 Kafka 通信，互不直接依赖
削峰填谷突发流量先写入 Kafka，消费者按能力慢慢消费
日志收集应用日志实时汇入 Kafka，供监控/分析系统消费
流处理配合 Kafka Streams / Flink 做实时计算

二、7 大核心组件

Broker 存，Topic 分类，Partition 分片，Replica 保高可。

组件一句话解释关键点
BrokerKafka 集群中的一台服务器多个 Broker 组成集群，负责存储消息和处理请求
Topic消息的逻辑分类（类似文件夹）生产者发往 Topic，消费者从 Topic 拉取
Partition（分区）Topic 的物理分片每个 Partition 内部严格有序，是高吞吐的基石
Replica（副本）Partition 的冗余备份Leader 负责读写，Follower 只同步（ISR 机制）
Offset（偏移量）消息在 Partition 中的唯一序号消费者通过 Offset 记录消费进度，重启不丢
Consumer Group多个消费者的集合组内一个分区只能被一个消费者消费，实现水平扩展
ZooKeeper / KRaft集群的"大脑"管理 Broker 元数据、Leader 选举；2.8+ 逐步用 KRaft 替代 ZK

记忆口诀：Broker 存数据，Topic 分类别，Partition 分片存，Replica 保高可，Offset 记进度，Group 管消费。

补充：Topic 是逻辑分类，Partition 是物理分片。一个 Topic 可以有多个 Partition，每个 Partition 是独立的物理日志文件。Kafka 的高吞吐靠 Partition 分片并行，不是单机性能强。

三、消费模式：Pull（拉取）

消费者自主控速 + 管理 Offset，空轮询用参数优化。

优点缺点
✅ 消费者自主控制速度，不会被洪流压垮 ❌ 分区没数据时，消费者空轮询造成资源浪费
✅ 自主管理 Offset，宕机重启也能断点续传 可通过 fetch.min.bytes / fetch.max.wait.ms 优化

四、ACK 机制详解

acks=0 最低，acks=1 中等，acks=all 最高。

ACK 值含义可靠性适用场景
acks=0发送出去就认为成功❌ 最低，可能丢失日志收集（允许丢少量）
acks=1（默认）Leader 写入成功即返回⚠️ 中等，Follower 未同步时 Leader 宕机 → 丢失一般业务场景
acks=all（或 -1）Leader 等待 ISR 所有副本确认✅ 最高，不丢失支付/交易等核心场景

生产者最佳实践：acks=all + retries=3 + enable.idempotence=true（开启幂等性，防止重复）。

补充：acks=1 不是"可靠"。Leader 写入成功就返回，但 Follower 还没同步，此时 Leader 宕机就会丢消息。核心业务必须用 acks=all，等 ISR 所有副本都确认才算成功。

五、如何保证消息不丢失（三端全链路）

生产端 acks=all，Broker 端禁脏选举，消费端先处理再提交。

端风险点解决方案
生产者端发送失败但不知道acks=all + retries 重试 + 幂等性
Broker 端Leader 切换导致数据未同步禁止不同步副本参与 Leader 选举（unclean.leader.election.enable=false）
消费者端先提交 Offset 再处理业务，业务失败 → 丢失关闭自动提交（enable.auto.commit=false），先处理业务，成功后再手动提交 Offset

六、如何保证消息不被重复消费（幂等性）

重复消费不可避免，消费端做幂等是关键。

重复消费的根因：Consumer 处理完业务，但在提交 Offset 前宕机了，重启后从旧 Offset 拉取 → 重复消费。

  • 消费端幂等：业务接口支持幂等（如用订单号 + 消息 ID 做唯一键防重）。
  • 生产者幂等：开启 enable.idempotence=true，Kafka 保证同分区内不重复。

面试标准答案："重复消费不可避免，关键是消费端做好幂等性，通过唯一键或状态机保证多次处理结果一致。"

七、如何保证消息顺序（分区有序）

只保证分区内有序，同 Key 进同分区 + 单线程消费。

核心原则：Kafka 只保证同一分区内有序，跨分区不保证。

端保证顺序的方式
生产者端相同 Key → 同一分区 → 保证顺序（按 key 哈希取模）；全局顺序（不推荐）= Topic 分区数设为 1
Broker 端天然保证同一分区写入顺序 = 存储顺序 = Offset 递增
消费者端一个分区在同一个消费组内只能被一个消费者消费（单线程串行）；max.in.flight.requests.per.connection=1 防止重试乱序

补充："全局顺序"和"分区顺序"是两回事。全局顺序要 Topic 分区数=1，彻底放弃并发，性能极差，一般不推荐；分区顺序靠相同 Key 进同一分区，既保顺序又保并发，是实际方案。

八、Leader 选举机制

旧版 ZK 临时节点，新版 KRaft Raft 共识。

版本选举方式关键机制
旧版（ZooKeeper）Broker 竞争在 ZK 上创建 /controller 临时节点首个成功创建的成为 Leader
新版（KRaft）基于 Raft 共识算法获得半数以上选票的节点成为 Active Controller

ISR（In-Sync Replicas）同步副本集合：与 Leader 保持实时同步的副本集合；决定 acks=all 时哪些副本写成功才算数；决定 Leader 宕机后谁能接管；通过 replica.lag.time.max.ms 动态维护。

补充：生产环境必须禁止从 ISR 之外选举 Leader（unclean.leader.election.enable=false）。否则一个没同步完的副本当 Leader，会丢消息——可靠性比可用性更重要。

九、消息重试与延迟机制

死信队列存失败消息，延时队列存定时消息。

概念作用典型场景
死信队列（DLQ）存放多次消费失败的消息消息重试达到上限后转入，待人工处理
延时队列存放指定时间后才可消费的消息订单超时关闭、定时任务、重试间隔控制

十、面试串联话术

架构→可靠性→顺序性→选型一气呵成。

Kafka 是分布式消息队列，核心能力是高吞吐低延迟。核心组件包括 Broker（存储节点）、Topic（逻辑分类）、Partition（物理分片，保证单分区有序）、Replica（副本保证高可用，ISR 机制决定同步和选举）。

消息可靠性上，生产端用 acks=all 配合重试，消费端先处理业务再提交 Offset，防止消息丢失。重复消费靠消费端幂等性兜底。顺序性靠相同 Key 进同一分区 + 单线程消费保证。

新版本已用 KRaft 替代 ZooKeeper，通过 Raft 共识选主，不再依赖外部协调组件。日志收集场景下，Kafka 是"活数据管道"，既能实时监控告警，又能供离线数仓做报表。
