DDD 对齐业务边界，充血内聚行为，先垂直后水平扩展。

一、DDD 领域驱动设计：实现流程

业务分析→模型草图→领域划分→细化设计→代码实现。

DDD 的核心是让代码结构对齐业务结构，先用通用语言沟通，再划边界、再写代码。五步从模糊到清晰：

步骤做什么关键产出记忆画面
业务分析梳理业务流程、角色、用例用例图、流程图先把"谁干什么"讲清楚
领域模型草图识别领域对象与关系概念草图白板上画圈连线
领域划分按业务边界划分子域子域列表把大蛋糕切成几块
细化设计定义聚合根、实体、值对象领域模型详图给每块蛋糕定主次
代码实现落地充血模型与分层可运行代码草图变工程

补充：DDD 不是分层架构。分层是技术维度（Controller/Service/Dao），DDD 是业务维度（按领域切分），两者正交——DDD 切横，分层切纵。

二、DDD 核心概念：领域、子域、限界上下文

子域切问题空间，限界上下文定模型边界。

概念定义作用记忆画面
领域一个业务范围/问题空间圈定要解决的业务"电商"整个大盘
子域领域内更小的业务块拆分复杂业务电商里的"商品、订单、支付"
核心域最赚钱、最关键的子域投入最精锐兵力电商的"交易"
支撑域必要但非核心的子域自建或外包均可电商的"物流"
通用域通用基础设施类子域直接用现成方案电商的"权限、认证"
限界上下文一个模型适用的明确边界防止概念混淆、定义契约"商品"在交易是 SKU，在仓储是货位

补充：子域是问题空间的划分（业务怎么切），限界上下文是解决方案空间的划分（模型边界在哪）。一个子域通常对应一个限界上下文，但不是绝对一对一。

三、聚合根、实体、值对象

聚合根是门面，实体有身份证，值对象看长相。

概念定义有无标识一致性职责记忆画面
聚合根聚合的入口对象，对外唯一引用点有 ID维护聚合内强一致性订单是根，订单项归它管
实体有唯一标识、有状态、可变有 ID聚合内参与一致性订单项有 ID，但要通过订单改
值对象无标识、不可变、用属性判等无 ID描述特征，无生命周期地址、金额、日期

关键规则：

  • 外部只能持有聚合根的引用，不能直接引用内部实体。
  • 聚合内修改必须经过聚合根，保证一致性边界。
  • 聚合间通过聚合根 ID 引用，不用对象引用。
  • 一个事务只改一个聚合，跨聚合用领域事件最终一致。

补充：实体和值对象的最大区别不是"复杂度"，而是有没有身份标识。Address 字段再多，两个相同就视为相等，它是值对象；OrderItem 只有一个数量字段，有 ID 能区分，它就是实体。

四、充血模型 vs 贫血模型

贫血=数据袋+Service大脑，充血=对象自己有大脑。

维度贫血模型充血模型
数据与行为对象只有数据（getter/setter），行为在 Service对象既有数据又有业务行为
业务逻辑位置全在 Service 层在领域对象内
面向对象退化成数据结构真正的封装
可维护性Service 越来越胖、难复用行为内聚、易测试
适用场景简单 CRUD、表驱动业务复杂业务规则、领域逻辑丰富
典型框架早期 Spring MVC + MyBatisDDD 项目、Spring Data + 领域层

补充：充血模型不是把所有逻辑塞进对象。领域逻辑（业务规则、状态变更）放领域对象；应用逻辑（事务编排、调用其他聚合、发事件）仍放 Application Service。充血的是领域层，不是把 Service 砍光。

五、垂直扩展 vs 水平扩展

垂直加硬件到顶，水平加节点无限，先垂直后水平。

维度垂直扩展（Scale Up）水平扩展（Scale Out）
做法增强单机硬件：加 CPU 核数、加内存、提磁盘 IOPS、加带宽增加更多服务器节点分散负载
上限有物理上限（单机硬件天花板）理论无上限（持续加节点）
成本越往上越贵（顶级硬件溢价高）线性成本，普通机器即可
单点风险高（单机故障全挂）低（节点故障可剔除）
改造成本几乎零改造需要分布式改造（状态、数据分片）
典型场景数据库单机升级、中间件初期Web 服务、微服务、分布式数据库

水平扩展的典型落地：

系统水平扩展方式记忆画面
OceanBase原生分布式数据库，加节点自动分片扩容加机器就自动切数据
Redis Cluster数据分散到多节点，16384 个槽位管理数据按槽位撒到多台
Spring Cloud / Dubbo应用服务多实例，注册中心 + 负载均衡同一个服务起 N 份

补充：垂直扩展和水平扩展不是二选一，而是先垂直后水平。单机没到瓶颈先加硬件（便宜、零改造），到顶了再水平扩展。一上来就分布式是过度设计。

六、架构演进：单体 → 集群 → 微服务 → 云原生

每步解一个问题、生一个新问题，匹配业务规模。

阶段形态解决的问题带来的新问题记忆画面
单体一个 war/jar 全包简单、好部署、好调试单点故障、代码膨胀、扩展难一间小作坊全干
集群单体多实例 + 负载均衡解决单点、提升吞吐Session 共享、状态同步同一家作坊开多家分店
微服务按业务边界拆分独立服务独立部署、独立扩展、技术异构分布式事务、链路追踪、运维复杂每道工序独立车间
云原生容器化 + K8s + 服务网格 + 弹性伸缩自动扩缩容、资源利用率高、故障自愈学习曲线陡、基础设施重车间全自动化、按需开关

演进触发条件：

  • 单体 → 集群：单机扛不住流量或不能停机。
  • 集群 → 微服务：团队规模变大、业务模块迭代节奏不一、需要技术异构。
  • 微服务 → 云原生：服务数量爆炸、需要弹性伸缩、多环境部署。

补充：微服务不是拆得越细越好。拆分粒度要匹配团队边界（康威定律）和业务边界（限界上下文）。拆太细会导致服务间调用爆炸、分布式事务遍地、运维成本失控。

七、高频场景题

Service 胖用 DDD 重构，QPS 涨先垂直后水平。

"业务越来越复杂，Service 层几千行，怎么重构？"

诊断：典型贫血模型症状——领域逻辑全堆在 Service，对象退化成数据袋。用 DDD 思路重构：先识别聚合根和实体，把业务规则从 Service 搬回领域对象，Service 只做事务编排。

"系统 QPS 涨了 10 倍，单机扛不住，怎么扩？"

诊断：先看瓶颈在哪。CPU/内存瓶颈先垂直扩展加硬件（零改造、见效快）；到顶或要抗单点再水平扩展。水平扩展前先解决无状态化（Session 外置、本地缓存改分布式），再起多实例 + 负载均衡。

"微服务拆分怎么定边界？拆太细调用爆炸怎么办？"

诊断：用 DDD 的限界上下文定边界——一个限界上下文对应一个微服务。拆分粒度匹配团队边界（康威定律），跨服务调用尽量走领域事件异步解耦，避免同步调用链过长。

八、面试回答模板

本质-机制-实战三句话讲清架构选型。

问题本质是：架构选型没有银弹，核心是"匹配业务规模和团队能力"，过度设计和设计不足都是错。

机制是：DDD 用领域边界对齐业务，充血模型把行为收回领域对象保证内聚；垂直扩展加硬件到顶，水平扩展加节点无限但需分布式改造；架构从单体到云原生，每一步解决一个核心矛盾。

实战中我会：先看业务复杂度决定要不要 DDD，简单 CRUD 用贫血模型够用；扩展先垂直后水平，水平前先无状态化；微服务按限界上下文拆，粒度匹配团队，跨服务用事件解耦。
