四种引用回收时机 + ThreadLocal 内存泄漏 + CAS 与 ABA + 连接池选型。

一、强软弱虚四种引用

强不回收、软 OOM 前、弱 GC 即、虚只跟踪。

引用类型回收时机典型场景记忆画面
强引用（Strong）永不回收，哪怕 OOM 也不动普通对象赋值 Object o = new Object()死忠保镖：人在保镖在
软引用（Soft）内存不足、OOM 前回收图片缓存、查询结果缓存备胎：够就留，紧张就丢
弱引用（Weak）只要发生 GC就回收，无论内存是否充足ThreadLocalMap key、WeakHashMap key、Guava/Caffeine 弱引用键值路人：GC 一来就走
虚引用（Phantom）最弱，唯一目的是跟踪 GC监控对象生命周期、清理外部资源、自定义内存管理侦探：只盯梢不碰对象

虚引用两个关键点：get() 永远返回 null（拿不到对象）；对象被回收时会被放入引用队列（ReferenceQueue），系统通知你"它没了"。

补充：软引用和弱引用最容易搞混。软引用看内存脸色（内存够就留，不足才回收），弱引用看 GC 脸色（GC 一来必回收，不管内存够不够）。一句话：软引用"留到 OOM 前"，弱引用"GC 即清"。

速记：强不回收、软 OOM 前、弱 GC 即、虚只跟踪。软留缓存、弱做映射、虚盯生命周期。

二、ThreadLocal 原理与内存泄漏

key 弱引用防 key 泄漏，value 强引用仍泄漏，finally 里 remove。

要点说明
原理每个线程持有自己的 ThreadLocalMap，以 ThreadLocal 对象为 Key 存数据
线程隔离不同线程访问同一 ThreadLocal 拿到各自独立的数据副本
应用场景同线程跨方法跨类传递上下文（用户身份、TraceId、数据库连接）
Entry 的 key弱引用，防止 ThreadLocal 对象本身无法被 GC
Entry 的 value强引用，key==null 后 value 仍被 Entry 持有 → 会泄漏
清理逻辑依赖 set/get/remove 中的清理逻辑，或显式调用 remove()
唯一彻底解法finally 块中调用 remove()

为什么 key 用弱引用？为了让 ThreadLocal 对象在没有外部强引用时能被 GC 回收，防止 key 本身造成内存泄漏。如果 key 是强引用，线程存活期间 ThreadLocal 永远回收不了。

value 会泄漏吗？会。因为 value 是强引用。当 key==null（弱引用被回收）后，value 仍被 Entry 持有，形成 Thread → ThreadLocalMap → Entry → value 的强引用链，线程不死 value 就不回收。线程池复用场景下尤其严重：线程长期存活，value 不断堆积，导致内存泄漏或数据串扰（前一个用户的上下文被后一个用户读到）。

补充："key 用弱引用"不等于"ThreadLocal 不会内存泄漏"。弱引用只防住了 key 泄漏，value 泄漏仍存在。唯一能彻底避免的方法是每次用完在 finally 块调用 remove()。很多人误以为用了弱引用就高枕无忧，结果线程池项目里照样 OOM。

速记：key 弱引用防 key 泄漏，value 强引用仍泄漏，finally 里 remove() 是唯一解。

三、CAS 原理与 ABA 问题

JNI→C→cmpxchg 原子指令，ABA 用版本号解决。

要点说明
全称Compare And Swap（比较并交换）
实现链路Java JNI → C 语言 → CPU 指令 cmpxchg
原子性来源CPU 指令级别原子，非锁实现
操作语义比较内存值与期望值，相等则更新为新值，不相等则不操作
Java APIcompareAndSwapxxx 系列（Unsafe）、Atomic* 原子类

ABA 问题：CAS 在操作前检查值有没有变化，没变化才更新。但如果值原来是 A，被其他线程改成 B 又改回 A，CAS 检查时发现"值没变"就更新了——实际却变化过。对纯数值更新无影响，但对"发生过修改就视为脏"的场景（如栈操作、状态机）会出错。

解决 ABA：给值加修改版本号。每次值变化都更新版本号，CAS 时不仅比值还比版本号。Java 中 AtomicStampedReference 用一个 (对象引用, 整数 stamp) 的 pair 对象解决 ABA——值改一次 stamp 加一，CAS 同时对比引用和 stamp。

补充：ABA 不是"值错了"，而是"值看起来没变但中间变过"。对只关心最终值的场景（计数器）ABA 无害；对关心过程的场景（资源状态、链表节点复用）ABA 有害，必须用版本号。别一提 CAS 就说"必须解决 ABA"，要看场景。

速记：CAS = JNI → C → cmpxchg 原子指令；ABA = A→B→A 检测不出，用版本号 AtomicStampedReference 解决。

四、数据库连接池性能对比

性能 HikariCP 最强，功能 Druid 最全。

连接池定位特点
HikariCP性能最强字节码优化、无锁设计、极致轻量
Druid功能最全SQL 拦截、统计全面、扩展性好
JDBC（无池）基线每次新建连接，性能最差
DBCP老牌功能基础，性能一般
C3P0（cp30）老牌性能最弱，已不推荐

性能排序：hikaricp > druid > jdbc > dbcp > cp30。

补充："性能最强"不等于"必须选"。HikariCP 极致性能但监控弱，Druid 性能略逊但 SQL 拦截、慢查询统计、防 SQL 注入等运维功能全面。互联网高并发业务选 HikariCP 榨干性能；需要强监控和 SQL 治理的传统企业系统选 Druid。

速记：性能 HikariCP > Druid > JDBC > DBCP > C3P0；功能 Druid 最全。

五、面试串联话术

引用→ThreadLocal→CAS→连接池一气呵成。

四种引用：强引用永不回收（哪怕 OOM），软引用 OOM 前回收（做缓存），弱引用 GC 即回收（做 ThreadLocalMap key、WeakHashMap key），虚引用最弱只跟踪 GC（get 永远返回 null，回收时入引用队列）。软引用看内存脸色，弱引用看 GC 脸色。

ThreadLocal：每线程一个 ThreadLocalMap 以 ThreadLocal 为 key 存独立副本，线程隔离。key 用弱引用防 key 泄漏，但 value 是强引用，key==null 后 value 仍被 Entry 持有，线程池复用下会内存泄漏或数据串扰。唯一解法是 finally 块调用 remove()。

CAS：JNI → C → CPU 指令 cmpxchg 原子操作，无锁比较并替换。ABA 问题是 A→B→A 检测不出，用版本号 AtomicStampedReference 解决（值改一次 stamp 加一，CAS 同时对比引用和 stamp）。连接池性能 HikariCP > Druid > JDBC > DBCP > C3P0，HikariCP 性能最强、Druid 功能最全。
