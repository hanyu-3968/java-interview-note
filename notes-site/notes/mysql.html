一、InnoDB vs MyISAM：怎么选存储引擎

事务行锁 InnoDB，MyISAM 只读快

两大存储引擎选型看业务：InnoDB 支持事务行锁适合高并发写，MyISAM 只读快适合历史归档。

维度InnoDBMyISAM
事务支持不支持
锁粒度行级锁表级锁
聚簇索引主键索引存整行索引存数据指针
COUNT(*)全表扫描直接返回计数器
适用场景高并发写、需要事务读多写少、历史归档

补充：InnoDB 的 COUNT(*) 慢不是缺陷——MVCC 下不同事务看到的行数不同，没法维护全局计数器；MyISAM 没事务没 MVCC 才能直接返回计数器。

二、B+树索引：聚簇索引 vs 二级索引

聚簇存整行，二级存主键要回表

B+树 多路平衡树，所有叶子在同一层，非叶子存键值加指针，叶子存数据。3 层可存约 2000 万行，磁盘友好每节点一页。

维度聚簇索引二级索引（非聚簇）
叶子节点完整行数据主键值
物理存储按主键顺序组织索引与数据分开
查询路径主键查询直达先查二级拿主键再回表
数量限制一张表只能一个可以有多个
优势场景主键查询、范围查询、返回多列覆盖索引、频繁插入非自增主键

补充：回表不是必须的——查询列全在二级索引里（覆盖索引）时直接返回免回表。InnoDB 无显式主键时选第一个不包含 NULL 的唯一索引作聚簇索引，再没有则自动生成隐式 ROW_ID，所以建表最好显式定义自增主键避免页分裂。

三、Redo Log 与 Undo Log：持久性与一致性

Redo 保持久重做，Undo 保回滚+MVCC

事务日志两件套：Redo Log 物理日志保证持久性，Undo Log 逻辑日志保证原子性和 MVCC。

维度Redo LogUndo Log
日志类型物理日志（页做了什么修改）逻辑日志（修改前的旧值）
存储位置redo log file回滚段 Rollback Segment
核心作用崩溃后重做，保证已提交不丢事务回滚 + 为 MVCC 提供旧版本
刷盘策略innodb_flush_log_at_trx_commit 每秒刷或每次提交刷随事务产生
一致性目标持久性（durability）原子性 + MVCC

补充：Redo Log ≠ Binlog。Redo 是 InnoDB 引擎层物理日志（循环写、crash-safe），Binlog 是 Server 层逻辑日志（追加写、主从复制），两者通过 2PC 保证一致。Undo 不只管回滚，还承担 MVCC 旧版本链。

四、MVCC 与四级隔离级别

RU 脏·RC 新快照·RR 复用防幻读·SR 串行

MVCC 通过 ReadView 快照实现并发读不阻塞写。四级隔离级别对应不同快照策略。

隔离级别快照机制脏读不可重复读幻读
读未提交 RU不用，直接读最新有有有
读已提交 RC每次 SELECT 生成新 ReadView无有有
可重复读 RR事务内复用同一 ReadView无无间隙锁解决
串行化 SR不用快照，加锁串行无无无

补充：不可重复读是同一条数据内容变了（别人修改提交），幻读是行数变了（别人插入/删除）。RR 靠间隙锁（Gap Lock）锁住索引范围空隙阻止插入来防幻读，RC 没有间隙锁所以仍有幻读。

五、二阶段提交 2PC 与 MySQL 内部 XA

先准备写双日志记 XID，崩了对账

分布式 2PC 有阻塞，MySQL 内部 2PC 用 XID 关联 binlog 与 redo 保证一致。

维度分布式 2PC3PC 改进MySQL 内部 XA
阶段Prepare + CommitCanCommit + PreCommit + DoCommitPrepare + Commit
Prepare冻结资源、锁定加询问阶段 + 超时InnoDB 写 Redo 标 PREPARED 记 XID
Commit全 OK 提交，任一失败回滚等不到指令超时自动提交Server 写 Binlog 带 XID 刷盘，通知 InnoDB 提交
缺点同步阻塞、单点故障仍可能不一致崩溃后对账恢复
崩溃恢复协调者崩了全卡死超时自动提交扫 Redo 找 PREPARED，去 Binlog 找 XID，有则提交无则回滚

补充：MySQL 内部 2PC ≠ 分布式 2PC。前者是 InnoDB Redo 与 Server Binlog 之间的一致性（同库内），后者是跨多个资源管理器的一致性（有协调者单点）。3PC 加超时但仍可能不一致，生产用得少。

七、SQL 执行流程：连分优执存

连接器→分析器→优化器→执行器→存储引擎

一条 SQL 走五步，日志三宝 undo/redo/binlog 协作保证回滚、持久、复制。

阶段职责关键点
连接器身份认证、连接管理长连接内存占用注意
分析器词法分析、语法分析解析成解析树
优化器选择最优执行计划可用 FORCE INDEX 纠正选错
执行器调用存储引擎接口操作 B+树Buffer Pool 没有则触发磁盘 IO
存储引擎真正读写数据InnoDB 操作 B+树

补充：MySQL 8.0 移除了查询缓存（Query Cache）——命中率太低（表一更新缓存全失效）。别在面试里说"先查缓存"，那是老版本。分页优化用 WHERE id > ? LIMIT ? 替代大 OFFSET。

八、数据库范式：1NF 到 5NF

1NF 列不可分·2NF 全依赖·3NF 无传递

范式要求反例
1NF列不可分电话列存两个号码
2NF非主键列完全依赖整个主键联合主键（订单ID,商品ID）中商品名只依赖商品ID
3NF非主键列不依赖其他非主键列订单表有客户ID又有客户姓名（姓名依赖客户ID）
4NF消除多值依赖课程表同时多教师多教材，拆两张表
5NF处理连接依赖拆到不能再拆，极少使用

补充：范式不是越高越好——3NF 通常够用，过度范式化会导致多表 JOIN 性能下降。实际业务常做适度反范式（冗余几列）换取查询性能。

九、索引优化：设计原则与失效场景

等值左范围右覆盖索引，左模糊函数类型错都失效

原则/场景说明
等值列放最左等值条件列放在联合索引最左
范围列放右边范围条件列放在等值列之后
覆盖索引索引包含查询所需全部列，免回表
左模糊失效LIKE '%abc' 走不了索引
函数操作失效WHERE UPPER(name)='JOHN' 走不了
隐式类型转换WHERE phone=123（phone 是 varchar）走不了
违反最左前缀跳过索引第一列，索引失效
范围后列失效WHERE age>20 AND name='张三' 只有 age 走索引
不等号/ORNOT IN、OR 两侧没都有索引则失效

补充：LIKE 'abc%' 能走索引（前缀确定），LIKE '%abc' 不能（左模糊无起点）。OR 不是一定失效——两侧列都有索引时走索引合并，任一侧没索引才退化为全表扫描。

高频场景题

"查 7 天内 status=APPLYING 的数据按 id 倒序，怎么优化索引？" 数据特征：7 天 100 万条，APPLYING 只有 100 条。推荐 INDEX idx_status_created_at(status, created_at)：status 等值过滤后只剩 100 条，即使有 filesort 排序开销也极小。高区分度且等值过滤的列放最左。

"InnoDB 聚簇索引和二级索引有什么区别？" 聚簇叶子存完整行数据，表按主键顺序组织，一张表只能一个；二级叶子存主键值，查询通常先查二级拿主键再回表，多一次 IO。覆盖索引可免回表。

"RR 级别下 InnoDB 怎么防止幻读？" RR 事务内复用同一 ReadView 解决不可重复读，再用间隙锁（Gap Lock）锁住索引范围空隙阻止插入，从而防幻读。RC 没有间隙锁所以仍有幻读。

面试回答模板

问题本质是：MySQL 的一致性靠"Redo/Undo 日志 + MVCC 快照 + 2PC 对账"三层保证，核心矛盾是"高并发下既要性能又要正确"。

机制是：Redo Log 物理日志保持久性，Undo Log 逻辑日志保回滚和 MVCC 旧版本；MVCC 用 ReadView 在 RC 每次新建、RR 事务内复用，配合间隙锁防幻读；2PC 用 XID 关联 binlog 与 redo，崩溃后对账保证主从不丢数据。

实战中我会：建表显式定义自增主键避免页分裂，索引按"等值左范围右覆盖索引"设计，慢查询用 FORCE INDEX 纠正优化器选错，分页用 WHERE id > ? LIMIT ? 替代大 OFFSET。

最后复习：闭眼回忆 8 句

  1. InnoDB 要事务行锁，MyISAM 只读快 count；COUNT(*) InnoDB 全扫是 MVCC 的锅不是缺陷。
  2. B+树聚簇索引存整行主键查极快，二级索引存主键要回表，3 层可存 2000 万行。
  3. 覆盖索引（查询列全在索引里）免回表；InnoDB 无显式主键选唯一索引或隐式 ROW_ID。
  4. Redo 物理日志保持久重做，Undo 逻辑日志保回滚和 MVCC 旧版本，刷盘看 innodb_flush_log_at_trx_commit。
  5. MVCC 四级隔离：RU 脏读、RC 每次新快照、RR 复用快照+间隙锁防幻读、SR 全锁串行。
  6. 不可重复读是同条数据内容变，幻读是行数变；RR 靠间隙锁（Gap Lock）防幻读。
  7. 2PC 先 Prepare 写双日志记 XID，Commit 写 binlog 带 XID；崩了重启对账，binlog 有就提交没有就回滚。
  8. 索引优化：等值左范围右覆盖索引少回表，左模糊/函数/类型错/违反最左前缀/OR 缺索引都失效。
