4 层加载器 + 双亲委派 + 资源加载同链 + SPI/Tomcat 打破。

一、类加载机制与类加载器类型

Bootstrap → Ext/Platform → App → 自定义，按需动态加载。

ClassLoader 的作用是将 class 文件加载到 JVM 虚拟机中，程序就可以正确运行。但 JVM 启动时并不会一次性加载所有 class 文件，而是根据需要动态加载。

类加载器层级加载范围实现语言
BootstrapClassLoader最顶层核心类库（lib 下的 Jar 包和 class 文件）C++ 实现
ExtentionClassLoader第二层%JAVA_HOME%/lib/ext 下的 jar 包和 class 类Java
AppClassLoader（SystemAppClass）第三层当前应用的 classpath 的所有类Java
自定义类加载器第四层开发者自定义加载路径Java

补充：JDK 9+ 把 ExtClassLoader 改名为 PlatformClassLoader（平台类加载器），加载范围也调整了。面试时如果提到 JDK 9 模块化，要说"ExtClassLoader 在 JDK 9 后变成 PlatformClassLoader"。

二、双亲委派机制

先委托父加载，父找不到子才自己加载。

核心原则：遇到加载请求，先把这个请求交给父加载器加载，只有父类加载器找不到 class 文件，子类才可以加载。

主要体现在 ClassLoader 的 loadClass() 方法中：

  1. 先检查是否已经被加载过。
  2. 若没有加载则调用父类加载器的 loadClass() 方法。
  3. 若父类加载器为空则默认使用启动类加载器作为父类加载器。
  4. 如果父类加载器加载失败，抛出 ClassNotFoundException 异常后，调用自己的 findClass() 方法进行加载。

双亲委派的作用：

  • 安全：防止核心类被恶意替换（自定义 java.lang.String 会被 Bootstrap 加载真正的 String）。
  • 唯一性：同一个类只会被加载一次，避免类的重复加载。

补充：双亲委派是"逻辑上的父子关系"，不是"继承关系"。类加载器通过 parent 字段持有父加载器引用，loadClass() 先委托 parent 加载，不是通过 extends 继承。

三、资源加载的委派流程

getResourceAsStream 走同一条委派链。

以 ParseKeyUtils.class.getClassLoader().getResourceAsStream("config/private.key") 为例：

步骤发生什么
1. 发起请求ParseKeyUtils 类由 AppClassLoader 加载，所以这次资源查找请求也是由 AppClassLoader 发起
2. 向上委托（第一步）AppClassLoader 收到请求后，不会立刻去 classpath 里找。它先把请求委托给它的父加载器 PlatformClassLoader（JDK 9 以前是 ExtClassLoader）
3. 继续向上（第二步）PlatformClassLoader 收到请求后，也不会自己去找，而是继续向上委托给自己的父加载器——BootstrapClassLoader
4. 父加载器查找（第三步）BootstrapClassLoader 检查自己负责的路径（JVM 核心库 rt.jar 等），看有没有 config/private.key。因为配置文件在项目的 classpath 下，不在 JVM 核心库里，所以它找不到，返回 null
5. 逐级向下查找（第四步）BootstrapClassLoader 返回 null 后，PlatformClassLoader 也在它自己的负责路径里找一遍，也找不到，返回 null。最终请求回到 AppClassLoader，它去自己的负责路径（项目的 classpath，即 target/classes 或 JAR 包内）查找，成功找到并返回文件流

速记：资源加载和类加载走同一条委派链——子加载器发起 → 一路向上委托到 Bootstrap → 逐级向下查找，找到就返回，找不到返回 null。

四、类加载的时机

new、静态访问、反射、子类先父类、主类。

JVM 不会一次性加载所有类，而是按需动态加载。

触发时机说明
实例化new 创建对象实例时
静态访问访问类的静态字段（非 final）或调用静态方法
反射通过反射访问类（Class.forName）
初始化子类初始化类时如果父类还没初始化，先初始化父类
主类JVM 启动时加载包含 main 方法的类

补充：类加载分为加载、链接（验证、准备、解析）、初始化五个阶段。"类加载的时机"指的是初始化时机，不是加载时机——加载可以提前，但初始化必须等到真正使用时。

五、打破双亲委派机制

SPI 用上下文类加载器，Tomcat 用 WebAppClassLoader。

双亲委派不是强制的，某些场景需要打破它实现灵活加载。

场景如何打破原因
SPI 机制（JDBC）用线程上下文类加载器（Thread Context ClassLoader）Bootstrap 加载 SPI 接口（如 java.sql.Driver），但实现类在 classpath 下，Bootstrap 看不到，需要用 AppClassLoader 反向加载
Tomcat每个 Web 应用有自己的 WebAppClassLoader，先自己加载再委派父同一 Tomcat 部署多个 Web 应用，可能依赖同一个库的不同版本，必须隔离
热部署自定义类加载器，重写 loadClass()每次修改类后用新类加载器重新加载，实现不重启更新
OSGi网状类加载结构模块化，每个模块有自己的类加载器，互相独立

补充：打破双亲委派不是"不用双亲委派"，而是"在特定场景下调整加载顺序"。Tomcat 的 WebAppClassLoader 对自己 Web 应用内的类先自己加载（打破），但对 JDK 核心类仍然委派给 Bootstrap（保留）——是"部分打破"。

六、面试串联话术

层级→委派→资源→打破一气呵成。

JVM 类加载器分四层：BootstrapClassLoader（C++ 实现，加载核心类库）、ExtClassLoader（加载 ext 目录，JDK 9 后改名 PlatformClassLoader）、AppClassLoader（加载 classpath）、自定义类加载器。

加载类时走双亲委派：子加载器先委托父加载器加载，父加载器找不到子加载器才自己加载。体现在 loadClass() 方法中——先检查是否已加载，再委托父加载器，父加载失败抛 ClassNotFoundException 后才调用自己的 findClass()。作用是安全（防止核心类被替换）和唯一性（同一类只加载一次）。

资源加载（getResourceAsStream）走同一条委派链。某些场景需要打破双亲委派：SPI 机制用线程上下文类加载器反向加载实现类，Tomcat 用 WebAppClassLoader 实现多应用依赖隔离。打破是"部分打破"，核心类仍委派 Bootstrap。
