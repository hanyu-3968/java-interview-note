NameServer 轻量路由 + CommitLog 顺序写 + 事务消息保金融级可靠。

一、核心组件

NameServer 路由，Broker 存储，Producer 写，Consumer 读。

组件职责关键点
NameServer轻量级路由中心对等集群，节点间无数据同步；Broker 心跳（30s）注册，超时（120s）剔除
Broker消息存储与转发的核心主从架构，Master 负责读写，Slave 备份；通过 CommitLog 顺序写入消息
Producer消息生产者从 NameServer 获取路由后与 Master 长连接；支持同步、异步、单向三种发送
Consumer消息消费者从 NameServer 获取路由后与 Broker 长连接拉取消息；支持推（Push）和拉（Pull）

补充：RocketMQ 的 NameServer 是对等集群，节点间不数据同步（与 ZK 不同）；Broker 30s 心跳注册，NameServer 120s 超时剔除。这是 RocketMQ 比 Kafka 轻量的原因——不依赖 ZK 的强一致。

二、核心工作流程

Broker 注册 → 获取路由 → 发送 → 存储 → 消费。

  1. Broker 启动注册：向所有 NameServer 节点注册自己的信息（IP、端口、Topic 等）。
  2. 获取路由：Producer/Consumer 从 NameServer 拉取最新 Broker 路由信息并缓存到本地。
  3. Producer 发送消息：根据路由与目标 Broker 的 Master 节点建立长连接，发送消息。
  4. Broker 存储消息：Master 收到消息后顺序写入 CommitLog 文件，并同步给 Slave 节点。
  5. Consumer 消费消息：根据路由与 Broker 的 Master 或 Slave 建立长连接，拉取消息消费。

三、如何保证消息不丢失

生产端同步发送+事务消息，Broker 同步刷盘+同步复制，消费端手动 ACK。

端风险点解决方案
生产者端 网络抖动导致发送失败 同步发送（阻塞等待确认，返回 SEND_OK 才成功）+ 失败重试（producer.setRetryTimesWhenSendFailed(3)）+ 事务消息（支付/订单等核心场景）
Broker 端 内存数据断电丢失 同步刷盘（flushDiskType=SYNC_FLUSH）+ 同步复制（brokerRole=SYNC_MASTER，Master 等 Slave 同步完才确认）
消费者端 先提交 Offset 再处理业务，业务失败 → 丢失 手动 ACK（关闭自动提交，业务成功后返回 CONSUME_SUCCESS）+ 失败重试（RECONSUME_LATER，默认重试 16 次后进死信队列）+ 幂等性处理

生产环境黄金组合：SYNC_MASTER + SYNC_FLUSH，实现消息零丢失。

补充：同步刷盘和同步复制是两个维度。同步刷盘防 Broker 宕机断电（单机），同步复制防 Master 宕机（集群）。两者都开才是金融级零丢失。

四、事务消息机制

两阶段提交 + 事务回查，最终一致性。

核心设计：两阶段提交（2PC）+ 事务补偿（回查），通过异步解耦避免传统 XA 事务锁资源、性能差的问题。

  1. 生产者向 RocketMQ 发送一条半消息，Broker 收到后回复 ACK，标记消息为暂不能投递。
  2. 生产者得到 ACK 后执行本地事务。
  3. 本地事务执行后向 Broker 发送二次确认（提交或回滚）；收到提交，Broker 将半消息标记为可投递。
  4. 事务回查机制：如果生产者执行完本地事务还没来得及发送二次确认就崩溃，Broker 通过定时任务主动扫描长时间处于半事务状态的消息；开发者需在生产者端实现回查逻辑（查数据库状态），根据结果返回提交或回滚。

补充：事务消息不是"消息发送和本地事务同时成功"。它是先发半消息（不投递）→ 执行本地事务 → 二次确认投递；如果二次确认丢失，Broker 回查补确认。本质是"最终一致性"，不是强一致。

五、如何保证消息顺序

分区有序：同 Key 进同队列 + 串行消费。

端保证顺序的方式
生产者端通过 MessageQueueSelector 将相同业务 Key（如订单号）的消息路由到同一个 MessageQueue
Broker 端将消息按顺序存入选定的 MessageQueue，不进行任何重排，只保证存储顺序与发送顺序一致
消费者端通过 MessageListenerOrderly 对同一队列进行串行消费

全局顺序：将队列数设为 1，但会极大影响性能，一般不推荐。

六、RocketMQ 与 Kafka 的 Topic 区别

Kafka Partition 独立日志，RocketMQ 合并写 CommitLog。

维度KafkaRocketMQ
Topic 存储Topic 直接拆分为 Partition，每个 Partition 是独立物理日志文件Topic 是纯逻辑概念，所有 Queue 的消息合并写入同一个全局 CommitLog
读写方式读写直接操作 Partition通过 ConsumeQueue 索引区分 Topic 和 Queue
优势简单直接顺序写入 CommitLog，极大提升单机吞吐量（避免随机写多个文件）

七、RocketMQ 与 Kafka 优缺点对比

Kafka 吞吐量+生态，RocketMQ 功能+金融级可靠。

对比维度Kafka 的优点RocketMQ 的优点
吞吐量与性能吞吐量极高，单机可达百万级 TPS吞吐量也很高，通常为十万级 TPS
消息与功能功能相对精简，专注于核心消息传输功能非常丰富，原生支持事务消息、严格顺序消息、死信队列、消息重试和定时消息
可靠性与一致性多副本保证高可用，但数据一致性不如 RocketMQ 严格金融级可靠性，同步双写 + Raft 协议，消息丢失概率极低
运维与生态生态强大，与 Flink/Spark 无缝集成；原生不带管理控制台自带功能完善的管理控制台；国内（阿里生态）应用广泛

选型结论：日志收集/大数据/极致吞吐量 + 对丢失/重复不敏感 → Kafka；订单/交易/支付/库存 + 顺序/一致性/可靠性严苛 → RocketMQ。

八、RocketMQ 为什么性能高

顺序写 + 零拷贝 + 索引分离三大支柱。

支柱原理效果
顺序写消息全部顺序追加到 CommitLog 文件磁盘顺序写的性能非常接近内存随机写，大大减少 IO 开销
零拷贝使用 mmap + write 的 transferTo 方法，数据从 PageCache 直接发送到 Socket 缓冲区避免内核态到用户态的数据拷贝，显著降低 CPU 占用
索引与数据分离ConsumeQueue 存储轻量索引（仅 20 字节/条），消费者先读索引定位物理偏移，再读 CommitLog大多数索引常驻内存，只有真实消息才触发磁盘 IO

九、死信队列与消息堆积处理

失败重试耗尽进死信，堆积先扩容再排查。

死信队列：消费失败且重试次数达到上限 → 死信队列。流程：初次消费失败 → 进入重试队列 → 重复重试次数耗尽 → 死信队列。

堆积可能原因排查方法解决方案
消费者能力不足看消费者机器 CPU/内存/网络 IO 是否跑满；看消费 TPS 是否远低于生产 TPS增加消费者实例或优化消费代码性能
下游依赖变慢消费者调用的数据库、API 接口响应时间（RT）突然升高优化下游接口性能；增加缓存；同步改异步
某条消息处理极慢查看消费日志，是否有某条消息处理时间远超平均水平优化这条消息的处理逻辑，或路由到专门的重试队列
消费者被阻塞消费者线程池满、死锁或频繁 Full GC分析堆栈（jstack），找出阻塞点，修复代码或增加线程池大小
生产者发送过快业务高峰期（如大促）流量暴增正常的流量削峰场景，消费者能力可动态扩容即良性积压

补充（线上实用技能）：堆积时如何在不重启服务的情况下临时跳过"卡住"的坏消息？利用 RocketMQ 的 Skip 死信机制（或重置消费点位），将消费者消费点位（Offset）手动向前移动 1 位，跳过那条一直处理失败的消息，让它进入死信队列（DLQ），等业务高峰期过了再从死信队列捞出来人工补处理。

十、定时消息（注意版本差异）

4.x 固定 18 级，5.0 任意时间戳。

版本支持方式代码
RocketMQ 4.x只支持 18 个固定级别（1s/5s/10s/30s...）message.setDelayTimeLevel(3)
RocketMQ 5.0支持任意时间延迟messageBuilder.setDeliveryTimestamp(System.currentTimeMillis() + 10 * 60 * 1000)

补充（保命认知）：RocketMQ 和 Kafka 在异常情况下都会产生重复消息。RocketMQ 只是概率比 Kafka 的 Rebalance 触发得低，但绝对不是"不会重复"。业务端做幂等（唯一业务 ID + Redis 或 DB 唯一键）是必须的，绝对不能依赖 MQ 来保证不重复。

十一、面试串联话术

架构→可靠性→事务→选型一气呵成。

因为我们做的是金融核心交易（退款/权益/发票），对数据一致性要求极高。选 RocketMQ 而不是 Kafka，核心就看中两点：

同步刷盘 + 同步复制：宁愿性能低一点（十万级 TPS 对我们足够），也要保证 Broker 宕机零丢消息。

事务消息：在处理"会员退款并撤销权益"时，我先发半消息，本地扣款成功后再 Commit，如果本地扣款失败就 Rollback。这保证了我的业务库和 MQ 里的下游通知是绝对一致的，彻底杜绝了"钱退了但权益没收回"的资损风险。
