对称快非对称慢，HTTPS 结合两者，防火墙三功能，DDoS 靠高防兜底。

一、常用加密算法：对称、非对称、摘要三分天下

对称一把钥匙快，非对称两把钥匙慢，摘要不可逆。

算法类型密钥长度安全性速度现状记忆画面
DES 对称 56 位 已被破解 快 已淘汰 老式挂锁，钥匙太短能暴力撬
3DES 对称 168 位（3×56） 较高 慢 逐步淘汰 三道挂锁叠一起，安全但费劲
AES 对称 128/192/256 位 高 快 主流 新式电子锁，又快又牢
SM4 对称 128 位 高 快 国密标准 国产电子锁，自主可控
RSA 非对称 1024/2048 位 高 慢 主流 信箱：公钥投信，私钥取信
MD5 摘要 无密钥 已不推荐 极快 仅做校验 指纹机：压一下出定长指纹

补充：MD5 不是"加密算法"，是摘要算法——有损压缩、不可逆，不能解密还原原文。说"MD5 加密密码"是口语化错误，准确说法是"MD5 摘要存密码"（且应加盐）。

对称 vs 非对称

维度对称加密非对称加密
密钥数量1 把（加解密共用）2 把（公钥加密、私钥解密）
速度快（适合大数据量）慢（比对称慢 100~1000 倍）
密钥分发难（如何安全把钥匙给对方？）易（公钥可公开，私钥自己留）
典型算法AES、DES、SM4RSA、ECC、SM2
适用场景数据加密密钥协商、数字签名

速记：对称快但分发难，非对称慢但分发易——所以 HTTPS 让非对称"送钥匙"，让对称"锁数据"。

补充：易混点——"公钥加密、私钥解密"用于保密通信；"私钥签名、公钥验签"用于身份认证。同一对密钥，用法相反，别搞反。

二、HTTPS 如何结合对称+非对称

非对称协商密钥，对称加密数据，兼顾安全与性能。

HTTPS = HTTP + TLS。核心思路：用非对称加密协商出对称密钥，之后全用对称加密传数据——既解决密钥分发，又保证传输速度。

步骤动作用什么
1客户端发起连接，带上自己支持的加密套件—
2服务端返回选定的加密套件 + 证书（含公钥）非对称（RSA/ECDHE）
3客户端验证证书（CA 签名、域名、有效期）数字签名
4客户端生成随机数，用服务端公钥加密发回非对称
5双方用该随机数算出对称会话密钥—
6之后所有数据用对称密钥加密传输对称（AES）

补充：非对称加密只在握手阶段用一次（协商密钥），握手完成后全部走对称加密。如果全程用 RSA 加密数据，性能会崩——这是 HTTPS 设计的精髓。现代 TLS 1.3 用 ECDHE 做密钥协商（前向安全：即使私钥泄露，历史流量也无法解密），RSA 只用于签名验证。

三、加密算法选型建议

数据加密选 AES/SM4，密钥协商选 RSA/SM2，密码存 bcrypt。

场景推荐算法原因
大数据量加密（接口/存储）AES-256 / SM4对称快、安全足够
密钥协商、数字签名RSA-2048 / SM2非对称解决分发
密码存储bcrypt / Argon2（加盐）慢哈希防彩虹表，MD5/SHA 已不推荐
完整性校验SHA-256 / HMACMD5 有碰撞，仅做非安全校验可用
国密合规场景SM2 + SM3 + SM4金融/政务强制要求

补充：易混点——"加密"和"哈希"不是一回事。加密可逆（能解密），哈希不可逆（不能还原）。密码要存哈希（不可逆），不能存加密（能被解出来）。速记：数据加密选 AES/SM4，密钥协商选 RSA/SM2，密码存储选 bcrypt，完整性校验选 SHA-256。

四、防火墙基本原理及功能

访问控制 + 数据包检查 + NAT 地址转换，三件事。

防火墙是网络边界的"门卫"，检查进出网络的每个数据包，按规则放行或拦截。

功能作用典型配置记忆画面
访问控制 只允许特定 IP/端口访问 放行 80/443，拦截其他 门卫查白名单，不在名单不让进
数据包检查 检测病毒、木马、攻击特征 匹配特征库拦截恶意包 安检机：包里有违禁品就扣下
地址转换（NAT） 内网私有 IP ↔ 公网 IP 多台内网共用一个公网 IP 出网 前台代收快递：对外只露前台地址

补充：易混点——NAT 不只是"省公网 IP"，更重要的是隐藏内网真实地址，外部只能看到公网出口 IP，无法直接访问内网服务器，相当于一层天然防护。防火墙分网络层（包过滤，看 IP/端口）和应用层（WAF，看 HTTP 内容防 SQL 注入/XSS）。

五、DDoS 攻击原理与防御

耗尽资源让服务不可用，SYN 洪水打半连接，靠高防+CDN+限频兜底。

DDoS（分布式拒绝服务）不偷数据、不破密码，只干一件事——用海量请求耗尽系统资源，让正常用户用不了服务。难缠在于攻击流量和正常流量难区分。

SYN 洪水攻击（最经典）

步骤正常连接SYN 洪水攻击
1客户端发 SYN攻击者发 SYN（伪造源 IP）
2服务端回 SYN-ACK，等客户端 ACK服务端回 SYN-ACK，等一个永远不来的 ACK
3客户端回 ACK，连接建立半连接队列被占满，正常用户无法建连
4数据传输服务资源耗尽，服务不可用

补充：易混点——SYN 洪水打的是半连接队列（服务端发了 SYN-ACK 还没收到 ACK 的连接），不是带宽。所以防御重点在"半连接管理"，不是单纯加带宽。

防御措施

措施作用记忆画面
高防 IP / 清洗设备流量先过清洗中心，过滤攻击流量再回源门口设安检门，可疑人员先筛掉
CDN 分散流量内容分发到多节点，单点被打不影响全局多开几个分店，砸一家还有其他家
防火墙限频限制单 IP 连接速率/并发数一个人一分钟只能进一次
SYN Cookie不分配资源就响应 SYN，ACK 回来才建连先发"预约号"，确认了才安排座位
监控+应急响应实时监控流量异常，触发应急预案装监控+保安巡逻，出事马上响应

速记：DDoS 防御四件套——高防清洗（过滤）、CDN 分散（多节点）、限频限连（卡单 IP）、监控应急（早发现早处理）。最关键是监控和应急响应，别等被打瘫了才发现。

补充：易混点——DDoS 是"耗资源"，DoS 是单点攻击。DDoS 难防就难在"分布式"——攻击源成千上万，封 IP 封不过来，必须靠清洗设备和 CDN 这种"基础设施级"防御。

六、高频场景题

接口被刷看监控，MD5 存密码不安全，HTTPS 不全用非对称。

"接口被刷爆，服务挂了，怎么判断是不是 DDoS？"先看监控——流量是否在短时间内暴涨数倍、来源 IP 是否极度分散（成千上万不同 IP）、半连接数是否飙升。如果三者同时出现，基本就是 DDoS。再看是带宽打满（流量型）还是资源耗尽（SYN 洪水型）：带宽打满看出口流量，资源耗尽看 netstat -an | grep SYN_RECV 半连接数。

"为什么 MD5 存密码不安全？该怎么存？"MD5 的问题不是"能被解密"（它不可逆），而是太快 + 有彩虹表——攻击者拿到 MD5 值后，可以用预计算的彩虹表反查出常见密码。正确做法是用 bcrypt / Argon2 这类慢哈希算法 + 加盐（每个用户随机盐），让暴力破解成本高到不划算。

"HTTPS 既然非对称加密安全，为什么不全用非对称？"非对称加密（RSA）比对称加密慢 100~1000 倍，全用非对称传数据性能会崩。所以 HTTPS 只在握手阶段用非对称协商出对称密钥，之后全用对称加密（AES）传数据——既解决密钥分发问题，又保证传输性能。
